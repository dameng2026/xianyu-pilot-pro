# 2026-08-08 滑块求解全量失败修复记录

## 现象

- 2026-08-06 ~ 08-07：滑块求解记录全部失败（08-07 共 259 条，0 成功）。
- 2026-08-07 20:41 后：不再产生新的滑块求解记录。
- 失败报错均为：
  `browserType.launchPersistentContext: Target page, context or browser has been closed`，
  Chrome 日志伴随 `No space left on device (28)`。

## 根因

`xianyu-crawler-service` 容器的 `/tmp` 是 2GB tmpfs。每次滑块求解会创建
`chrome-slider-temp-*` 临时 Chrome profile；Python 子进程被 `pkill -9` 或异常退出时
`finally` 清理不执行，残留目录持续累积。08-07 白天求解频繁后 `/tmp` 被 116 个目录
占满（约 1.8GB，使用率 100%），Chrome 无法写入 profile / crashpad，导致所有浏览器
启动全部失败。

08-07 20:41 后无新记录，是因为所有 cookie 有效的账号均已恢复 WS 连接，不再触发求解；
但环境仍是坏的，一旦再触发必失败。

## 修复

1. 清理线上 `xianyu-crawler-service` 容器 `/tmp` 中的历史残留
   （`chrome-slider-temp-*`、`chrome-slider-warm-*`、`com.google.Chrome.*` 等，
   保留 `xya-slider-seed-v2` / `xya-slider-persistent-v3` / 全局锁）。
2. `apps/crawler-service/sliderSolve.py`：
   - 每次启动浏览器前执行 `ensure_temp_space()`：清理超过 30 分钟的临时 profile /
     单例锁文件；空间低于 512MB 时紧急清理超过 5 分钟的残留。
3. `apps/crawler-service/Dockerfile`：
   - 容器入口启动 5 分钟周期的后台清扫任务（删除超过 30 分钟的 Chrome 临时目录），
     防止未来再次占满 `/tmp`。
4. `docker-compose.yml`：
   - `crawler-service` / `crawler-worker` 的 `/tmp` 从 2g 扩到 4g；
   - `shm_size` 从 1g 扩到 2g；
   - 健康检查增加 `/tmp` 可用空间 > 256MB 的检查，空间不足时容器提前
     `unhealthy`。
5. 线上 `.env.production` 内存配额（实测内存充足）：
   - `AUTOMATION_API_MEMORY_LIMIT_BYTES`：1GB → 2GB
   - `AUTOMATION_WORKER_MEMORY_LIMIT_BYTES`：768MB → 1.5GB
   - `CRAWLER_WORKER_MEMORY_LIMIT_BYTES`：1GB → 2GB
   - `CRAWLER_API_MEMORY_LIMIT_BYTES` 保持 8GB

- 本次验证的 5 次求解均为“未检测到滑块”（`captchaDetected=false`，免滑块路径），
  因为测试账号 cookie 本身有效、WS 可用。真实出现 Baxia 滑块挑战时的拖动成功率
  尚未获得新的样本；历史数据中浏览器拖动路径成功率较低。若后续真实滑块挑战
  成功率低于预期，需要单独优化拖动算法/代理出口，而不是环境容量问题。
- 迁移/发布记录：本次为 crawler 环境与脚本热修复，未涉及数据库迁移；
  生产发布通过服务器端 `docker compose build + up -d --force-recreate` 完成。
