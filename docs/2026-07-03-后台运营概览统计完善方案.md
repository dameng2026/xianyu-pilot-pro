# 后台运营概览页面统计完善方案

> 分析日期：2026-07-03
> 分析范围：admin-web 运营概览页 + 全平台数据资产盘点
> 目标：找出运营概览统计缺口，提出高效实用的完善方案

---

## 一、运营概览现状分析

### 1.1 页面定位

运营概览是 admin-web 后台首页，路由 `/admin/dashboard/overview`，实际渲染组件为
`apps/admin-web/src/views/admin/module/index.vue`（当 `moduleKey === 'dashboard'` 时走专用仪表盘模板）。

数据由 `AdminModuleController`（`/admin-api/admin/dashboard/*`）提供，首屏通过聚合接口
`getDashboardInit()` 一次拉取全部数据（缓存 30 秒）。

### 1.2 当前展示的统计内容

| 区块 | 展示内容 | 数据来源 |
|------|----------|----------|
| 顶部统计卡（9 张） | 账号数、商品总数、在售商品、今日订单、今日销售额、AI回复、发货成功、发货失败、待发货 | `summary()` 实时聚合 |
| 业务趋势柱状图 | 近 7/30/90 天的订单、发货、AI 三色柱状 | `trend?range=` |
| 实时监控（6 项） | 在线账号、今日发布、今日成交额、AI 调用、AI 失败、工作流执行中 | `realtime-stats` |
| 待处理事项（≤8 条） | 工作流失败、风控账号、通知发送失败、卡密低库存 | `pending-tasks` |
| Top 5 热销商品 | 热销商品排名（日销≥5） | `top-hot-goods` ← `hot_goods_stat` 表 |
| 风控分布 | 5 级风控账号数量 | `risk-distribution` |
| 系统健康 | core-api / automation-service / crawler-service 三服务状态 | `system-health` |
| 最近后台操作 | 操作日志时间线 | `recent-events` |

### 1.3 现有统计的优点

- 首屏聚合加载，性能较好（30 秒缓存）
- 覆盖了核心交易闭环（账号→商品→订单→发货→AI回复）
- 有趋势图、待办事项、系统健康，结构较完整
- 利用 `dashboard_daily_stat` 预聚合表 + 实时聚合双策略

### 1.4 核心问题

**统计维度偏窄，仅覆盖"闲鱼交易闭环"，缺少平台运营全局视角。** 具体缺口：

| 缺口 | 影响 |
|------|------|
| 无平台用户/租户统计 | 看不到注册量、活跃度、增长趋势 |
| 无收入与财务统计 | 看不到平台真实营收、AI 成本利润 |
| 无工作流运营统计 | 工作流数据在监控页，概览页看不到执行概况 |
| 无消息/客服效率统计 | 看不到咨询量、响应时长、自动回复覆盖率 |
| 无账号健康趋势 | 只有风控静态分布，无健康分变化趋势 |
| 无卡密库存统计 | 仅在待办里出现低库存告警，无全局库存视图 |
| 无通知投递统计 | 通知成功/失败率不可见 |
| 无客户端错误监控 | 前端报错不可见 |
| 无商机发掘统计 | 商机挖掘使用量、AI 生图量不可见 |
| 无定时任务统计 | 任务执行情况不可见 |
| 无类目真实销售 | `CategorySalesVO.salesCount` 直接复用 goodsCount，非真实销量 |
| 无订单转化漏斗 | 看不到 下单→付款→发货→完成 的转化率 |

## 二、全平台数据资产盘点

经全面分析，平台共有 **40+ 张数据表**，分布在 3 个数据库中，可统计的数据源远超当前概览展示。

### 2.1 核心业务时序表（可直接做趋势图）

| 表名 | 业务含义 | 时序字段 | 可统计指标 |
|------|----------|----------|------------|
| `xianyu_trade_order` | 订单主表 | create_time / pay_time / ship_time / confirm_time | 订单量、成交额、转化漏斗、付款时效、发货时效 |
| `xianyu_trade_order_item` | 订单项 | created_time | 商品维度销量、类目销量 |
| `delivery_record` | 发货记录 | created_time | 发货量、成功率、失败原因分布、重试率 |
| `auto_reply_log` | 自动回复日志 | created_time | 命中量、命中率、规则效果、AI vs 关键词占比 |
| `xianyu_chat_message` | 聊天消息（高频） | message_time | 消息量、活跃时段、双向消息比 |
| `xianyu_conversation` | 会话 | last_message_time / created_time | 会话量、完结率 |
| `xianyu_account_health_snapshot` | 账号健康快照 | collected_time | 健康分趋势、API 成功率、WS 延迟 |
| `operation_log` | 操作日志 | created_time | 操作活跃度、高风险操作频次 |
| `notification_delivery_log` | 通知投递日志 | created_time | 投递量、成功率、耗时、渠道分布 |
| `client_error_log` | 前端错误日志 | created_time | 错误量、错误类型分布 |
| `workflow_execution` | 工作流执行 | started_time / finished_time | 执行量、成功率、平均耗时 |
| `workflow_node_log` | 工作流节点日志 | started_time / finished_time | 节点级耗时、瓶颈分析 |
| `opportunity_image_history` | 商机生图历史 | created_time | AI 生图量、模型使用分布 |
| `goofish_crawl_jobs`(PG) | 爬虫任务 | created_at | 爬取任务量、成功率 |

## 三、建议新增的统计模块

按运营重要性排序，分为 **P0（必做）/ P1（重要）/ P2（增强）** 三级。

### P0 - 平台运营核心指标（当前完全缺失）

#### 模块 1：平台用户与租户统计

**目的**：掌握平台用户规模与增长，这是 SaaS 平台运营的第一指标。

| 指标 | 数据来源 | 实现方式 |
|------|----------|----------|
| 平台用户总数 | `sys_user` COUNT | 实时聚合 |
| 今日新增用户 | `sys_user` WHERE DATE(created_time)=CURDATE() | 实时聚合 |
| 近 30 天新增趋势 | `sys_user` GROUP BY DATE(created_time) | 新增 Mapper 方法 |
| 活跃租户数 | `xianyu_account` DISTINCT tenant_id | 实时聚合 |
| 会员等级分布 | `xianyu_account_membership` GROUP BY membership_level | 新增 Mapper 方法 |

#### 模块 2：收入与成本统计

**目的**：平台管理者最关心的"赚了多少、花了多少、利润多少"，当前完全不可见。

| 指标 | 数据来源 | 实现方式 |
|------|----------|----------|
| 今日平台收入 | 支付订单表 SUM(amount) WHERE status=成功 AND DATE=今日 | 新增支付订单 Mapper |
| 今日 AI 成本 | AI 计费表 SUM(cost) WHERE DATE=今日 | 复用 `AiBillingService` |
| 今日利润 | 收入 - AI 成本 | 计算得出 |
| 近 30 天收入趋势 | 支付订单 GROUP BY DATE | 新增 Mapper |
| 近 30 天 AI 成本趋势 | AI 计费 GROUP BY DATE | 复用 `AdminMonitoringController` 数据 |
| Token 充值总额 | 支付订单 SUM WHERE type=充值 | 新增 Mapper |

#### 模块 3：订单转化漏斗

**目的**：发现交易环节的流失点，当前只有订单总量无转化分析。

| 指标 | 数据来源 | 实现方式 |
|------|----------|----------|
| 下单数 → 付款数 → 发货数 → 完成数 | `xianyu_trade_order` 按 order_status 分组 COUNT | 新增 Mapper 方法 |
| 付款转化率 | 已付款 / 已下单 | 计算得出 |
| 发货转化率 | 已发货 / 已付款 | 计算得出 |
| 完成转化率 | 已完成 / 已下单 | 计算得出 |
| 平均付款时长 | AVG(pay_time - create_time) | 新增 Mapper |
| 平均发货时长 | AVG(ship_time - pay_time) | 新增 Mapper |

### P1 - 运营效率指标（当前部分缺失）

#### 模块 4：消息与客服效率

**目的**：衡量自动回复/AI 客服的运营效率。

| 指标 | 数据来源 | 实现方式 |
|------|----------|----------|
| 今日消息量 | `xianyu_chat_message` COUNT WHERE DATE=今日 | 新增 Mapper |
| 今日会话数 | `xianyu_conversation` COUNT WHERE DATE(created_time)=今日 | 复用 `countDaily` |
| 自动回复覆盖率 | auto_reply_log 命中数 / 消息总数 | 计算得出 |
| AI 回复占比 | auto_reply_log WHERE hit_type=ai / 总命中数 | 复用 `countByAction` |
| 平均首次响应时长 | 需从消息对计算 | 较复杂，可后置 |
| 活跃时段分布 | `xianyu_chat_message` GROUP BY HOUR(message_time) | 新增 Mapper |

#### 模块 5：工作流运营统计

**目的**：工作流是核心自动化能力，概览页应展示执行概况（当前仅在独立监控页）。

| 指标 | 数据来源 | 实现方式 |
|------|----------|----------|
| 工作流定义总数 | `workflow_definition` COUNT | Python 端聚合 |
| 今日执行次数 | `workflow_execution` COUNT WHERE DATE=今日 | Python 端聚合 |
| 今日成功率 | 成功数 / 总数 | 计算得出 |
| 平均执行耗时 | AVG(finished_time - started_time) | Python 端聚合 |
| 近 7 天执行趋势 | GROUP BY DATE(started_time) | Python 端聚合 |
| 当前执行中数 | WHERE status=running | Python 端聚合 |

#### 模块 6：账号健康趋势

**目的**：当前只有风控静态分布，缺少健康分变化趋势。

| 指标 | 数据来源 | 实现方式 |
|------|----------|----------|
| 平均健康分 | `xianyu_account_health_snapshot` AVG(health_score) 最新一批 | 复用 `findLatestByAccountId` |
| 平均 API 成功率 | 同上 AVG(api_success_rate) | 同上 |
| 平均 WS 延迟 | 同上 AVG(ws_latency_ms) | 同上 |
| 近 7 天健康分趋势 | GROUP BY DATE(collected_time) AVG(health_score) | 新增 Mapper |
| Cookie 即将过期数 | `xianyu_account_auth` WHERE token_expire_time < NOW()+3天 | 新增 Mapper |

#### 模块 7：卡密库存统计

**目的**：卡密是发货资源，库存不足会导致发货失败。

| 指标 | 数据来源 | 实现方式 |
|------|----------|----------|
| 卡密组总数 | `card_group` COUNT | 复用现有 |
| 总库存 / 已用 / 剩余 | `card_item` GROUP BY status COUNT | 复用 `statsByGroupIds` |
| 低库存组数（< 阈值） | `card_group` WHERE remain_count < alert_threshold | 新增 Mapper |
| 库存使用率 | 已用 / 总数 | 计算得出 |
| 近 7 天消耗趋势 | `card_item` WHERE status=1 GROUP BY DATE(used_time) | 新增 Mapper |

### P2 - 增强型监控指标

#### 模块 8：通知投递统计

| 指标 | 数据来源 |
|------|----------|
| 今日通知投递量 | `notification_delivery_log` COUNT |
| 投递成功率 | success=1 / total |
| 渠道分布 | GROUP BY channel_key |
| 平均投递耗时 | AVG(cost_ms) |

#### 模块 9：客户端错误监控

| 指标 | 数据来源 |
|------|----------|
| 今日前端错误数 | `client_error_log` COUNT |
| 错误类型 Top 5 | GROUP BY error_type ORDER BY COUNT DESC |
| 近 7 天错误趋势 | GROUP BY DATE |

#### 模块 10：商机发掘统计

| 指标 | 数据来源 |
|------|----------|
| 今日商机搜索次数 | 商机搜索日志 |
| 今日 AI 生图次数 | `opportunity_image_history` COUNT WHERE DATE=今日 |
| 生图模型使用分布 | GROUP BY model |
| 爬虫任务执行统计 | `goofish_crawl_jobs`(PG) |

#### 模块 11：商品同步与类目分析

| 指标 | 数据来源 |
|------|----------|
| 今日商品同步次数 | `xianyu_goods_sync_task` COUNT |
| 同步成功率 | status=completed / total |
| 类目商品数分布 | `xianyu_goods` GROUP BY category |
| 类目真实销量 | `xianyu_trade_order_item` JOIN `xianyu_goods` GROUP BY category（修复当前假数据） |

## 四、建议新增/扩展的统计表

### 4.1 扩展 `dashboard_daily_stat` 表（强烈建议）

当前预聚合表只有 11 个字段，建议新增以下字段以支撑更丰富的趋势图：

```sql
ALTER TABLE dashboard_daily_stat ADD COLUMN new_user_count INT DEFAULT 0 COMMENT '当日新增用户数';
ALTER TABLE dashboard_daily_stat ADD COLUMN active_tenant_count INT DEFAULT 0 COMMENT '当日活跃租户数';
ALTER TABLE dashboard_daily_stat ADD COLUMN platform_revenue DECIMAL(12,2) DEFAULT 0 COMMENT '当日平台收入';
ALTER TABLE dashboard_daily_stat ADD COLUMN ai_cost DECIMAL(12,2) DEFAULT 0 COMMENT '当日AI成本';
ALTER TABLE dashboard_daily_stat ADD COLUMN ai_call_count INT DEFAULT 0 COMMENT '当日AI调用次数';
ALTER TABLE dashboard_daily_stat ADD COLUMN workflow_execution_count INT DEFAULT 0 COMMENT '当日工作流执行数';
ALTER TABLE dashboard_daily_stat ADD COLUMN workflow_success_count INT DEFAULT 0 COMMENT '当日工作流成功数';
ALTER TABLE dashboard_daily_stat ADD COLUMN avg_health_score DECIMAL(5,2) DEFAULT 0 COMMENT '当日平均账号健康分';
ALTER TABLE dashboard_daily_stat ADD COLUMN card_consume_count INT DEFAULT 0 COMMENT '当日卡密消耗数';
ALTER TABLE dashboard_daily_stat ADD COLUMN notification_count INT DEFAULT 0 COMMENT '当日通知投递数';
ALTER TABLE dashboard_daily_stat ADD COLUMN notification_success_count INT DEFAULT 0 COMMENT '当日通知投递成功数';
ALTER TABLE dashboard_daily_stat ADD COLUMN client_error_count INT DEFAULT 0 COMMENT '当日客户端错误数';
ALTER TABLE dashboard_daily_stat ADD COLUMN order_paid_count INT DEFAULT 0 COMMENT '当日付款订单数';
ALTER TABLE dashboard_daily_stat ADD COLUMN order_shipped_count INT DEFAULT 0 COMMENT '当日发货订单数';
ALTER TABLE dashboard_daily_stat ADD COLUMN order_completed_count INT DEFAULT 0 COMMENT '当日完成订单数';
```

**同步更新**：`DashboardDailyStat.java` 实体、`DashboardDailyStatMapper.java`、ETL 定时任务。

### 4.2 新增 `platform_revenue_daily_stat` 表（财务专用）

如果不想让 `dashboard_daily_stat` 过于臃肿，可单独建财务统计表：

```sql
CREATE TABLE platform_revenue_daily_stat (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    tenant_id BIGINT,
    stat_date DATE NOT NULL,
    payment_amount DECIMAL(12,2) DEFAULT 0 COMMENT '支付收入',
    token_recharge_amount DECIMAL(12,2) DEFAULT 0 COMMENT 'Token充值金额',
    ai_cost DECIMAL(12,2) DEFAULT 0 COMMENT 'AI成本',
    ai_token_consumed BIGINT DEFAULT 0 COMMENT 'AI Token消耗',
    profit DECIMAL(12,2) DEFAULT 0 COMMENT '利润(收入-成本)',
    payment_order_count INT DEFAULT 0 COMMENT '支付订单数',
    UNIQUE KEY uk_tenant_date (tenant_id, stat_date)
);
```

### 4.3 新增 `workflow_daily_stat` 表（工作流专用）

工作流数据在 Python 侧，建议建表做预聚合：

```sql
CREATE TABLE workflow_daily_stat (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    tenant_id BIGINT,
    stat_date DATE NOT NULL,
    definition_count INT DEFAULT 0 COMMENT '工作流定义总数',
    execution_count INT DEFAULT 0 COMMENT '执行次数',
    success_count INT DEFAULT 0 COMMENT '成功次数',
    fail_count INT DEFAULT 0 COMMENT '失败次数',
    avg_duration_ms BIGINT DEFAULT 0 COMMENT '平均执行耗时(ms)',
    publish_count INT DEFAULT 0 COMMENT '发布商品数',
    image_generated_count INT DEFAULT 0 COMMENT '生图数量',
    UNIQUE KEY uk_tenant_date (tenant_id, stat_date)
);
```

### 4.4 新增 `message_daily_stat` 表（消息/客服专用）

`xianyu_chat_message` 数据量大，实时聚合性能差，建议预聚合：

```sql
CREATE TABLE message_daily_stat (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    tenant_id BIGINT,
    account_id BIGINT,
    stat_date DATE NOT NULL,
    total_message_count INT DEFAULT 0 COMMENT '消息总数',
    received_count INT DEFAULT 0 COMMENT '接收消息数',
    sent_count INT DEFAULT 0 COMMENT '发送消息数',
    auto_reply_count INT DEFAULT 0 COMMENT '自动回复数',
    ai_reply_count INT DEFAULT 0 COMMENT 'AI回复数',
    conversation_count INT DEFAULT 0 COMMENT '会话数',
    new_conversation_count INT DEFAULT 0 COMMENT '新会话数',
    UNIQUE KEY uk_tenant_account_date (tenant_id, account_id, stat_date)
);
```

### 5.2 交互优化建议

1. **指标卡支持点击下钻**：点击"今日订单"跳转订单管理页，点击"今日收入"跳转财务明细页
2. **趋势图支持指标切换**：除了时间范围切换，增加指标维度切换（订单/发货/AI/收入/成本）
3. **对比数据**：每个指标卡显示环比（vs 昨日）和同比（vs 上周同日）变化率，绿色↑红色↓
4. **告警优先级排序**：待处理事项按严重程度排序，高风险置顶
5. **数据刷新策略**：
   - 核心指标卡：30 秒缓存（保留现有）
   - 趋势图：5 分钟缓存（变化不频繁）
   - 系统健康：10 秒轮询
   - 待处理事项：30 秒轮询
6. **暗色模式适配**：如 admin-web 支持主题切换，确保图表配色兼容

### 5.3 性能优化建议

1. **预聚合表 ETL 定时刷新**：每小时刷新一次 `dashboard_daily_stat` 当日数据，避免实时聚合
2. **首屏聚合接口保持**：`getDashboardInit()` 模式很好，新增模块也并入此接口
3. **趋势图走预聚合表**：新增字段后，趋势图全部走 `dashboard_daily_stat`，避免实时 GROUP BY
4. **Python 侧数据通过 Java 聚合**：工作流统计由 Java 调 Python 后聚合，前端只请求 Java 一个接口
5. **大表查询加索引**：
   - `xianyu_chat_message` 已有索引，按天聚合 OK
   - `client_error_log` 确保 `created_time` 有索引
   - `notification_delivery_log` 确保 `created_time` 有索引

## 七、总结

当前运营概览页的统计覆盖了闲鱼交易闭环的核心指标，但作为 **SaaS 平台管理后台**，缺少三个关键维度：

1. **平台经营视角**：用户规模、收入成本、利润——管理者最关心的数据完全缺失
2. **运营效率视角**：消息客服效率、工作流执行概况、账号健康趋势——自动化效果不可衡量
3. **风险监控视角**：通知投递、客户端错误、卡密库存——系统可靠性不可见

平台已有 **40+ 张数据表**、**10+ 个已有聚合 Mapper 方法**，数据资产丰富，但概览页只用了其中约 30%。
通过扩展预聚合表字段、新增 3-4 个统计模块、优化页面布局，即可将运营概览从"交易看板"升级为"平台运营全景看板"。

建议按 P0 → P1 → P2 三阶段实施，第一阶段即可补齐最关键的平台经营指标。
