> **版本**：v1.0
> **日期**：2026-07-30
> **作者**：AI 架构分析
> **状态**：待评审
> **目标读者**：项目负责人、后端工程师、前端工程师、运维

---

## 摘要

小梦客服（`setting_key: xiaomeng-assistant`）的设计目标是"帮助用户完成权限内的所有操作"。但实际线上表现是：**前台调用工具时频繁出现"查询不到任何数据"或"调用失败"**，几乎所有用户操作都无法完成。

经过对 `apps/automation-service/app/services/ai_cs_runtime.py`、`apps/automation-service/app/services/ai_cs_tools.py`、`apps/core-api/.../AiCsController.java`、`apps/core-api/.../AiCsService.java`、`apps/user-web/src/components/AiCsPanel.vue` 等核心文件的完整调研，确认问题根因是**架构层面的设计缺陷**，而非个别 bug：

1. **写操作工具链路从设计上就是断的**：5 个串联 bug 让"用户点确认按钮"这条路从未真正工作过——前端拿到的 `toolCallId` 永远是 `0`，对 `0` 直接 return 不发请求，即使绕过前端，Java 也不传 `tool/arguments` 给 Python，Python 回查表的字段名还写错。**所有 19 个写操作类工具从上线第一天起就完全无法执行**。
2. **查询类工具的"查不到数据"由 SQL 设计缺陷导致**：`list_refunds` 的兜底逻辑是死代码、`list_orders` 的 LEFT JOIN 退化成 INNER JOIN、`search_goods_online` 不检查 cookie_status 导致选到失效账号、多工具仅按 `tenant_id` 过滤在多用户场景下越权或漏数据。
3. **异常吞噬让所有失败都变成"稍后重试"**：13 处 except 只记 `errorType` 不记堆栈、`search_goods_online` 用 `if False else` 强制吞掉真实错误信息——线上日志根本看不出真正失败原因。
4. **工具调用协议是脆弱的自定义协议**：基于 markdown 代码块正则匹配（` ```tool_call {...}``` `），不走 OpenAI 标准 function calling，LLM 输出格式稍有偏差就解析失败。工具结果**不会回灌给 LLM 继续推理**，无法完成多步骤任务。
5. **`user_id` 校验策略不一致**：`list_accounts` 有三层兜底，但 `reply_buyer_message`/`get_fish_shop_data`/`list_products` 等工具严格匹配无兜底，早期账号 `user_id` 未回填时直接失败。

本报告基于以上发现，提出**全新架构方案**：以"OpenAI 标准 function calling + Agent 多轮推理 + 风险分级自动执行 + 统一账号上下文 + 全链路可观测"为核心，重新设计小梦客服工具调用体系，确保"用户权限内的所有操作都能完成"。

## 一、现状与问题

### 1.1 现有架构

小梦客服与自动回复客服是两个独立配置：

| 维度 | `xiaomeng-assistant`（小梦运营助手） | `ai-customer-service`（自动回复买家） |
|------|------------------------------------|--------------------------------------|
| 触发方式 | 前台用户主动对话（PC 端聊天窗） | 买家发消息时后端被动触发 |
| 工具调用 | 支持 19+ 个工具 | 不支持工具调用（只生成回复文本） |
| systemPrompt 来源 | 代码硬编码"小梦人设" + 用户自定义追加 | 完全用户自定义 |

本报告聚焦 **`xiaomeng-assistant`（小梦主动对话模式）**，因为用户反馈的"AI 客服帮用户完成所有操作"对应的就是这个模式。

### 1.2 工具调用全链路

## 二、根因分析

### 2.1 P0：写操作工具链路从设计上就是断的

**5 个串联 bug 让所有 19 个写操作类工具从上线第一天起就完全无法执行。**

#### 根因 #1：`AiCsService.logToolCall` 定义但从未被调用

- **位置**：`apps/core-api/src/main/java/com/xianyu/admin/service/AiCsService.java:562-580`
- **证据**：全项目 grep `\.logToolCall\(` 与 `aiCsService\.logToolCall` 均为零匹配
- **后果**：`ai_cs_tool_call` 表（schema 见 `apps/core-api/src/main/resources/db/migration/V1.39__add_ai_cs_tables.sql:81-95`）永远没有数据写入

#### 根因 #2：Java `complete` 接口未返回 `toolCallIds`，Python 拿到的 `real_tool_call_id` 永远是 0

- **位置**：`apps/core-api/src/main/java/com/xianyu/admin/service/AiCsService.java:551-556`
- **证据**：`appendAssistantMessageAndCharge` 返回字段只有 `messageId / tokensCharged / balanceAfter / deducted / chargeError`，**没有 `toolCallIds` 字段**
- **后果**：Python 在 `ai_cs_runtime.py:1356-1362` 试图从 `complete_resp.get("toolCallIds")` 提取真实 ID，永远是 `None`，最终 `real_tool_call_id = 0`（`ai_cs_runtime.py:1362`），发送给前端的 `toolCallId` 字段也永远是 `0`（`ai_cs_runtime.py:1450`）

#### 根因 #3：前端对 `toolCallId=0` 直接 return，用户点确认按钮无任何响应

- **位置**：`apps/user-web/src/components/AiCsPanel.vue:847`
- **证据**：
  ```javascript
  if (!sessionId.value || !msg.toolCallId) return
  ```
  JavaScript 中 `0` 是 falsy，`!msg.toolCallId` 为 `true`，函数直接返回
- **后果**：UI 显示工具卡片和"确认/拒绝"按钮，但用户点击按钮**完全无响应**，不发送任何请求

#### 根因 #4：Java `confirmTool` 不传 `tool` / `arguments` 给 Python

- **位置**：`apps/core-api/src/main/java/com/xianyu/admin/controller/AiCsController.java:293-311`
- **证据**：
  ```java
  Map<String, Object> req = new LinkedHashMap<>();
  req.put("sessionId", sessionId);
  req.put("userId", userId);
  req.put("tenantId", tenantId);
  req.put("toolCallId", toolCallId);
  req.put("accept", accept);
  // 缺少 req.put("tool", ...) 与 req.put("arguments", ...)
  ```
- **后果**：Python `/tool/execute` 端点拿不到 `tool_name`，进入回查逻辑

#### 根因 #5：Python 回查 `ai_cs_tool_call` 时字段名错误

- **位置**：`apps/automation-service/app/api/v1/routes/ai_cs.py:294-298`
- **证据**：
  ```python
  row = (await db.execute(_text("""
      SELECT tool_name, arguments_json FROM ai_cs_tool_call
      WHERE id = :id AND tenant_id = :tenant_id LIMIT 1
  """), ...))
  ```
  但 V1.39 schema 实际字段名是 `arguments`，不是 `arguments_json`
- **后果**：即使表里有数据，也因字段名不匹配查不到

#### 根因 #6：`execute_confirmed_tool` 在 `tool_name` 为空时直接返回失败

- **位置**：`apps/automation-service/app/services/ai_cs_runtime.py:1519-1532`
- **证据**：
  ```python
  if not tool_name:
      await call_java_tool_result(...)
      return { "status": "failed", "result": {"error": "工具名为空"}, ... }
  ```
- **后果**：因根因 #4 和 #5，`tool_name` 必然为空，工具执行必然失败

#### 串联结论

```
logToolCall 没人调用 → ai_cs_tool_call 表为空
                                  ↓
Java 不返回 toolCallIds → Python real_tool_call_id=0
                                  ↓
前端拿到 toolCallId=0 → 点击按钮直接 return
                                  ↓
即使绕过前端 → Java confirmTool 不传 tool/arguments
                                  ↓
Python 回查表 → 字段名写错 + 表本来就空
                                  ↓
tool_name 必为空 → execute_confirmed_tool 直接 fail
```

**这条链路从设计上就是断的，从未真正工作过。**

### 2.2 P1：查询类工具"查不到数据"

#### 根因 #7：`list_refunds` 兜底逻辑是死代码

- **位置**：`apps/automation-service/app/services/ai_cs_tools.py:1404-1550`
- **证据**：注释（line 1417-1419）声称"通过 join `xianyu_account.user_id` 严格匹配 + tenant_id 兜底"，但主查询 SQL（line 1438-1449）**根本没有任何 user_id 条件**：
  ```python
  sql = ("SELECT ... FROM xianyu_refund r "
         "LEFT JOIN xianyu_account a ON a.id = r.account_id "
         "WHERE r.tenant_id = :tenant_id AND r.deleted = 0")
  ```
  兜底查询 SQL（line 1476-1486）与主查询几乎完全相同，两次查询执行同样的 SQL
- **后果**：浪费一次 DB 调用，兜底逻辑完全无效

#### 根因 #8：`list_orders` 的 LEFT JOIN 退化为 INNER JOIN

- **位置**：`apps/automation-service/app/services/ai_cs_tools.py:1163-1172`
- **证据**：
  ```python
  # 注释：使用 LEFT JOIN 避免账号被删除时订单查不到
  sql = ("SELECT ... FROM xianyu_trade_order o "
         "LEFT JOIN xianyu_account a ON a.id = o.account_id "
         "WHERE o.tenant_id = :tenant_id AND o.deleted = 0 "
         "AND (a.deleted = 0 OR a.deleted IS NULL)")  # ← 与注释自相矛盾
  ```
- **后果**：账号被软删除（`a.deleted=1`）的订单被过滤掉，与注释意图相反

#### 根因 #9：`search_goods_online` 自动选号不检查 `cookie_status`

- **位置**：`apps/automation-service/app/services/ai_cs_tools.py:2243-2249`
- **证据**：
  ```python
  cookie_row = (await db.execute(
      select(XianyuAccount.id, XianyuAccount.cookie).where(
          XianyuAccount.tenant_id == tenant_id,
          XianyuAccount.user_id == user_id,
          XianyuAccount.deleted == 0,
          XianyuAccount.cookie.isnot(None),  # ← 只检查 cookie IS NOT NULL
      ).order_by(XianyuAccount.id.asc()).limit(1)
  )).one_or_none()
  ```
- **后果**：可能选到 `cookie_status` 已失效/已过期的账号，导致后续 MTOP 调用失败

#### 根因 #10：部分工具严格校验 `user_id` 但无兜底，早期账号失败

| 工具 | 文件:行号 | 现象 |
|------|----------|------|
| `reply_buyer_message` | `ai_cs_tools.py:2403` | `if owner_row is None or int(owner_row or 0) != user_id: return _fail("账号不存在或无权访问")` |
| `get_fish_shop_data` | `ai_cs_tools.py:2502` | 同上 |
| `list_products` | `ai_cs_tools.py:437` | 同上 |
| `create_auto_reply_rule` | `ai_cs_tools.py:552` | 同上 |
| `create_delivery_rule` | `ai_cs_tools.py:621` | 同上 |
| `create_scheduled_task` | `ai_cs_tools.py:953` | 同上 |
| `prepare_product_publish` | `ai_cs_tools.py:2991` | 同上 |

- **对比**：`list_accounts` 有三层兜底（严格 user_id → tenant 范围 → 含软删除，line 167-209）
- **后果**：早期账号 `user_id` 未回填时，用户问"我的账号"能查到（走兜底），但接着问"账号 X 的订单"会失败（无兜底，user_id 严格校验失败）—— 这种**不一致体验**是用户反馈"AI 客服时好时坏"的直接原因

#### 根因 #11：多工具仅按 `tenant_id` 过滤，多用户共享 tenant 时数据越权或漏数据

| 工具 | 文件:行号 | 备注 |
|------|----------|------|
| `list_orders` | `ai_cs_tools.py:1170` | 完全不用 user_id |
| `get_account_summary` | `ai_cs_tools.py:1230` | 完全不用 user_id |
| `get_dashboard_summary` | `ai_cs_tools.py:1813, 1826, 1840` | 三个子查询都只用 tenant_id |
| `list_recent_conversations` | `ai_cs_tools.py:2325` | 完全不用 user_id |
| `list_refunds` | `ai_cs_tools.py:1447` | 注释说用但实际未用 |
| `get_sales_comparison` | `ai_cs_tools.py:2590` | 完全不用 user_id |

- **后果**：如果租户下有多个用户（如主账号 + 子账号），会查到其他用户的数据；若业务模型是"单用户=单 tenant"则漏数据风险较低，但越权风险仍在

### 2.3 P1：异常吞噬让问题不可见

#### 根因 #12：13 处 except 只记 errorType 不记堆栈

所有工具的 except 块都使用 `logger.warning(... errorType=%s, type(exc).__name__)` 模式，**丢失了堆栈和具体错误信息**，导致日志无法定位真正失败原因：

| 位置 | 文件:行号 |
|------|-----------|
| build_system_prompt 失败 | `ai_cs_runtime.py:1226-1229` |
| 加载历史消息失败 | `ai_cs_runtime.py:1260-1263` |
| LLM 调用失败 | `ai_cs_runtime.py:1280-1283` |
| 查询工具 commit 失败 | `ai_cs_runtime.py:1378-1381` |
| 查询工具 execute 失败 | `ai_cs_runtime.py:1383-1387` |
| 摘要 complete 失败 | `ai_cs_runtime.py:1442-1446` |
| execute_confirmed_tool commit 失败 | `ai_cs_runtime.py:1547-1550` |
| 摘要生成失败 | `ai_cs_runtime.py:1576-1580` |
| 摘要 complete 失败 | `ai_cs_runtime.py:1602-1606` |
| execute_tool 调度器异常 | `ai_cs_tools.py:3483-3488` |
| list_orders 异常 | `ai_cs_tools.py:1207-1212` |
| list_refunds 异常 | `ai_cs_tools.py:1544-1549` |
| 几乎所有其它工具 | `ai_cs_tools.py` 全文同模式 |

#### 根因 #13：`execute_tool` 调度器 TypeError 只记 info 级别

- **位置**：`apps/automation-service/app/services/ai_cs_tools.py:3476-3482`
- **证据**：`except TypeError as exc: logger.info(...)`
- **后果**：必填参数缺失（如 `create_card_group` 缺 `group_name`）会被工具内部 if 检查拦截；这里的 TypeError 实际是 SQLAlchemy 或其它库内部错误被误分类，但因为只记 info 级别不告警

#### 根因 #14：`search_goods_online` 用 `if False` 强制吞掉错误信息

- **位置**：`apps/automation-service/app/services/ai_cs_tools.py:2294`
- **证据**：
  ```python
  return _fail(f"搜索商品失败：{exc}"[:200] if False else "搜索商品失败，请稍后重试")
  ```
- **后果**：`if False else` 让前半部分永远不执行，真实异常信息被强制丢弃

### 2.4 P2：工具调用协议脆弱

#### 根因 #15：基于 markdown 代码块正则匹配，非 OpenAI function calling

- **位置**：`apps/automation-service/app/services/ai_cs_runtime.py:62-63, 464-467`
- **证据**：
  ```python
  _TOOL_CALL_MARKER = "tool_call"
  _TOOL_CALL_PATTERN = re.compile(r"```tool_call\s*(\{.*?\})\s*```", re.DOTALL)
  ```
- **后果**：
  - LLM 输出格式稍有偏差（多余空格、换行、JSON 字段顺序变化）就解析失败
  - 解析失败时整条 AI 输出被当作纯文本回复展示给用户，**用户看到 `tool_call` 代码块**（违反 prompt 中"绝不向用户展示 ```tool_call 代码块"的约束）
  - 无法支持主流 LLM 的原生 function calling 能力，无法利用模型对该协议的优化训练

#### 根因 #16：工具结果不会回灌给 LLM 继续推理

- **位置**：`apps/automation-service/app/services/ai_cs_runtime.py:1365-1432`
- **证据**：工具执行后调用 `call_java_tool_result()` 持久化 + `generate_summary()` 让 AI 把工具结果翻译成自然语言，**摘要直接展示给用户，流程结束**
- **后果**：无法完成多步骤任务（如"查询所有销量为 0 的商品并删除"），无法基于工具结果决定下一步动作

#### 根因 #17：`TOOL_DEFINITIONS` 参数 schema 不规范

- **位置**：`apps/automation-service/app/services/ai_cs_tools.py:3094-3418`
- **证据**：parameters 用字符串描述类型，不是 JSON Schema：
  ```python
  {
      "name": "list_orders",
      "parameters": {
          "accountId": "int (可选) 闲鱼账号ID，不传则查全部账号",
          "status": "int (可选) 订单状态 0-5",
      },
  }
  ```
  系统提示中拼接方式（`ai_cs_runtime.py:409`）：
  ```python
  params_str = ", ".join(f"{k}: {v}" for k, v in tool_def["parameters"].items())
  ```
  生成 `- list_orders(accountId: int (可选)..., status: int (可选)...): ...`
- **后果**：参数描述混在函数签名里，LLM 容易混淆必填/可选、参数类型、参数约束

#### 根因 #18：系统提示过长（30KB 知识库 + 20 条历史 + 详细人设）

- **位置**：`apps/automation-service/app/services/ai_cs_runtime.py:359`
- **证据**：`_GLOBAL_KB_CHAR_BUDGET = 30 * 1024`
- **后果**：30KB 知识库 + 20 条历史消息（每条 1200 字）+ 详细人设，容易超出模型上下文上限，LLM 可能忽略后段工具说明

### 2.5 P2：一致性问题

- 见 §2.2 根因 #10，这是设计层面的不一致

#### 根因 #20：`reply_buyer_message` 构造 `mock_current_user` 只传 `tenant_id` 不传 `user_id`

#### 根因 #21：`httpx.AsyncClient` 每次新建，不复用连接池

## 三、新方案设计

### 3.1 设计原则

| 原则 | 说明 |
|------|------|
| **协议标准化** | 采用 OpenAI 标准 function calling（`tool_calls` + `tool_results`），主流 LLM 都原生支持，避免脆弱的 markdown 解析 |
| **多轮推理** | 工具结果回灌给 LLM，支持 ReAct/Agent 模式，可串联完成多步骤任务（如"查询销量为 0 的商品并删除"） |
| **风险分级自动执行** | 只读工具直接执行；变更类工具按风险等级自动放行 / 二次确认 / 完全禁用，避免"所有写操作都要点确认"的低效体验 |
| **统一账号上下文** | 所有涉及账号的工具共用同一份 `AccountContext`，统一选号策略、统一 user_id 兜底、统一 cookie_status 校验 |
| **全链路可观测** | 每次 chat 生成 traceId，所有工具调用、LLM 调用、Java 回调都打 traceId；落库到 `ai_cs_tool_call` 表；失败时记录完整堆栈 |
| **错误对 LLM 友好** | 工具失败时返回结构化错误（含错误码、原因、建议下一步动作），让 LLM 能自动重试或换路径 |
| **性能优先** | httpx 连接池复用、并行调用、元数据缓存，单轮工具调用响应时间 < 500ms（不含 LLM 推理） |
| **安全优先** | RBAC 工具权限矩阵、操作日志可审计、敏感操作可撤销 |

#### 3.3.3 Agent 多轮推理循环

```python
# ai_cs_runtime.py (重构后)
MAX_TOOL_ROUNDS = 8  # 单次对话最多 8 轮工具调用, 防止死循环

async def agent_loop(
    db: AsyncSession,
    *,
    session_id: int,
    user_id: int,
    tenant_id: int,
    user_message: str,
    trace_id: str,
) -> AsyncGenerator[SseEvent, None]:
    # 1. 构造 messages: 系统提示 + 历史消息 + 用户消息
    messages = await build_messages(db, session_id, tenant_id, user_id, user_message)
    tools = await build_tools_schema(tenant_id, user_id)  # 根据权限过滤可用工具

    # 2. Agent 循环
    for round_idx in range(MAX_TOOL_ROUNDS):
        yield sse_event("round_start", {"round": round_idx, "traceId": trace_id})

        llm_resp = await call_llm_with_tools(messages, tools, scene="ai_cs_chat")
        await persist_assistant_message(db, session_id, llm_resp, trace_id)
        messages.append(llm_resp.to_message())

        if llm_resp.content:
            yield sse_event("assistant_delta", {"content": llm_resp.content})

        if not llm_resp.tool_calls:
            # LLM 不再调用工具, 结束循环
            yield sse_event("assistant_done", {})
            break

        # 3. 执行所有 tool_calls
        for tool_call in llm_resp.tool_calls:
            tool_name = tool_call.function.name
            arguments = json.loads(tool_call.function.arguments)

            yield sse_event("tool_start", {
                "toolCallId": tool_call.id,
                "toolName": tool_name,
                "arguments": arguments,
                "traceId": trace_id,
            })

            # 4. 风险分级决策
            risk = await classify_risk(tool_name, arguments, tenant_id, user_id)
            if risk.level == "auto":
                result = await execute_tool(db, tool_name, arguments,
                                            tenant_id=tenant_id, user_id=user_id,
                                            trace_id=trace_id)
            elif risk.level == "confirm":
                # 发送确认请求, 等待用户响应
                yield sse_event("tool_confirm_request", {
                    "toolCallId": tool_call.id,
                    "toolName": tool_name,
                    "arguments": arguments,
                    "preview": risk.preview,  # 影响预览
                    "reason": risk.reason,
                })
                approved = await wait_for_user_confirmation(
                    session_id, tool_call.id, timeout=120
                )
                if not approved:
                    result = {"success": False, "error": "用户拒绝执行"}
                else:
                    result = await execute_tool(db, tool_name, arguments,
                                                tenant_id=tenant_id, user_id=user_id,
                                                trace_id=trace_id)
            else:  # blocked
                result = {"success": False, "error": f"工具 {tool_name} 当前用户无权执行"}

            # 5. 持久化 tool_call 记录 + 回灌给 LLM
            await persist_tool_call(db, session_id, tool_call.id, tool_name,
                                    arguments, result, trace_id)
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": format_tool_result_for_llm(tool_name, result),
            })

            yield sse_event("tool_result", {
                "toolCallId": tool_call.id,
                "success": result.get("success"),
                "summary": result.get("summary"),
                "traceId": trace_id,
            })

    else:
        # 达到最大轮次仍未结束
        yield sse_event("assistant_done", {
            "reason": "max_rounds_reached",
            "message": "已达到最大工具调用轮次, 请继续提问或细化需求",
        })
```

### 3.4 风险分级与执行策略

#### 3.4.1 风险等级定义

| 等级 | 行为 | 适用工具特征 |
|------|------|--------------|
| `auto` | 自动执行, 仅记录日志 | 只读查询、聚合统计、Token 余额查询 |
| `confirm` | 弹卡片, 用户点"批准"后执行 | 变更类操作（创建/更新/删除）、对外发送消息、调用闲鱼接口 |
| `blocked` | 完全禁用, 不允许调用 | 跨租户操作、危险命令、未授权功能 |

#### 3.4.4 风险分级决策流程

```python
async def classify_risk(
    tool_name: str,
    arguments: dict,
    tenant_id: int,
    user_id: int,
) -> RiskDecision:
    policy = await load_risk_policy(tool_name)

    # 1. 检查用户权限（基于 RBAC）
    if not await user_can_use_tool(user_id, tool_name):
        return RiskDecision(level="blocked", reason="当前用户无权使用此工具")

    # 2. 检查调用频率
    if await exceed_call_limit(user_id, tool_name, window="hour"):
        return RiskDecision(level="blocked", reason="调用频率超限, 请稍后再试")

    # 3. 检查账号归属（涉及账号的工具）
    if policy.requires_account_owner and "accountId" in arguments:
        if not await user_owns_account(user_id, tenant_id, arguments["accountId"]):
            return RiskDecision(level="blocked", reason="账号不属于当前用户")

    # 4. 生成影响预览
    preview = await generate_preview(tool_name, arguments) if policy.risk_level == "confirm" else None
    # 例如: delete_product 预览 "将删除商品《xxx》(软删除, 可在回收站恢复)"
    #       reply_buyer_message 预览 "将向买家 xxx 发送消息: ..."

    return RiskDecision(
        level=policy.risk_level,
        preview=preview,
        reason=policy.description,
    )
```

### 3.5 统一账号上下文 AccountContext

#### 3.5.1 问题

现有实现中，每个工具独立处理 `user_id` 兜底、`cookie_status` 校验、自动选号，导致：
- 策略不一致（`list_accounts` 有兜底，`list_products` 没兜底）
- `search_goods_online` 不检查 `cookie_status`，可能选到失效账号
- `reply_buyer_message` 用 `mock_current_user` 只传 `tenant_id` 不传 `user_id`

#### 3.5.2 解决方案：统一 AccountContext

```python
# ai_cs_tools.py (重构后)
class AccountContext:
    """
    用户可访问的账号上下文。所有涉及账号的工具必须通过此上下文获取账号。
    统一处理 user_id 兜底、cookie_status 校验、自动选号。
    """

    def __init__(self, db: AsyncSession, tenant_id: int, user_id: int):
        self.db = db
        self.tenant_id = tenant_id
        self.user_id = user_id
        self._accounts_cache: list[AccountInfo] | None = None

    async def list_accessible_accounts(
        self,
        *,
        include_deleted: bool = False,
        only_active: bool = False,
    ) -> list[AccountInfo]:
        """
        返回当前用户可访问的所有账号。
        兜底策略(与 list_accounts 现有三层兜底一致, 全工具复用):
          1. 严格匹配: tenant_id + user_id + deleted=0
          2. 兜底1: tenant_id + deleted=0 (适用早期 user_id 未回填)
          3. 兜底2: tenant_id (含软删除, 仅 include_deleted=True 时)
        """
        if self._accounts_cache is not None:
            return self._accounts_cache

        # 第一层: 严格匹配
        rows = await self._query_accounts(
            tenant_id=self.tenant_id,
            user_id=self.user_id,
            deleted=0,
        )
        self._fallback_reason = None

        # 第二层: tenant 范围兜底
        if not rows:
            rows = await self._query_accounts(
                tenant_id=self.tenant_id,
                deleted=0,
            )
            if rows:
                self._fallback_reason = (
                    f"按当前用户ID（{self.user_id}）严格匹配未找到账号, "
                    f"已回退到租户范围查询, 共 {len(rows)} 个账号"
                )

        # 第三层: 含软删除
        if not rows and include_deleted:
            rows = await self._query_accounts(tenant_id=self.tenant_id)
            if rows:
                self._fallback_reason = f"已展示该租户下全部 {len(rows)} 个账号（含已禁用账号）"

        self._accounts_cache = [AccountInfo.from_row(r) for r in rows]
        return self._accounts_cache

    async def select_account_for_external_call(self) -> AccountInfo | None:
        """
        为对外调用(发送消息/搜索商品/取鱼小铺数据)选择一个可用账号。
        策略:
          - cookie_status=1 (正常) 优先
          - cookie 非空
          - 按 id 升序(稳定可预测)
          - 自动轮询: 失败后下次自动切换到下一个账号
        """
        accounts = await self.list_accessible_accounts(only_active=True)
        # 过滤 cookie 有效的账号
        usable = [a for a in accounts if a.cookie and a.cookie_status == 1]
        if not usable:
            return None
        # 简单轮询策略(基于时间分桶, 确保多账号负载均衡)
        idx = int(time.time() / 60) % len(usable)
        return usable[idx]

    async def validate_account_access(self, account_id: int) -> AccountInfo:
        """
        校验用户对指定账号的访问权限。
        统一兜底逻辑: 严格匹配 -> tenant 范围兜底
        """
        accounts = await self.list_accessible_accounts()
        for acc in accounts:
            if acc.id == account_id:
                return acc
        raise AccountAccessDeniedError(
            f"账号 {account_id} 不存在或无权访问"
        )

    @property
    def fallback_reason(self) -> str | None:
        """兜底原因(若有), 供 LLM 向用户说明"""
        return self._fallback_reason
```

# ai_cs_tools.py
class ToolRegistry:
    _tools: dict[str, ToolDefinition] = {}
    _handlers: dict[str, Callable] = {}

    @classmethod
    def register(cls, definition: ToolDefinition, handler: Callable):
        cls._tools[definition.name] = definition
        cls._handlers[definition.name] = handler

    @classmethod
    async def get_available_tools(cls, tenant_id: int, user_id: int) -> list[dict]:
        """根据用户权限过滤可用工具, 返回 OpenAI tools schema"""
        allowed = await get_user_allowed_tools(user_id)
        return [
            cls._tools[name].to_openai_schema()
            for name in allowed
            if name in cls._tools
        ]

    @classmethod
    async def execute(
        cls,
        tool_name: str,
        arguments: dict,
        *,
        db: AsyncSession,
        account_ctx: AccountContext,
        trace_id: str,
    ) -> ToolResult:
        handler = cls._handlers.get(tool_name)
        if not handler:
            return _fail(f"未知工具: {tool_name}")
        try:
            return await handler(db, account_ctx=account_ctx, trace_id=trace_id, **arguments)
        except ToolArgumentError as e:
            return _fail(f"参数无效: {e}")
        except Exception as e:
            logger.exception(f"工具执行失败 tool=%s traceId=%s", tool_name, trace_id)
            return _fail(f"工具执行失败: {type(e).__name__}: {str(e)[:200]}")

    code: str  # 错误码: ARGUMENT_INVALID / ACCOUNT_NOT_FOUND / COOKIE_EXPIRED / ...

            "error": self.message,
            "code": self.code,
            "detail": self.detail,
            "retryable": self.retryable,
            "suggested_next_action": self.suggested_next_action,
        }, ensure_ascii=False)

#### 3.8.2 工具级重试策略

```python
# 仅对瞬时错误重试, 业务错误(如账号不存在)不重试
RETRYABLE_ERRORS = {
    "DB_TIMEOUT",
    "DB_CONNECTION_LOST",
    "REDIS_TIMEOUT",
    "HTTP_5XX",
    "HTTP_TIMEOUT",
}

async def execute_with_retry(
    handler: Callable,
    *,
    max_retries: int = 1,
    retry_delay: float = 0.5,
) -> ToolResult:
    last_error = None
    for attempt in range(max_retries + 1):
        try:
            return await handler()
        except RetryableError as e:
            last_error = e
            if attempt < max_retries:
                await asyncio.sleep(retry_delay)
                continue
            return _fail(ToolError(
                code=e.code,
                message="工具暂时不可用, 请稍后重试",
                detail=str(e),
                retryable=True,
            ))
        except BusinessError as e:
            # 业务错误不重试, 直接返回
            return _fail(ToolError(
                code=e.code,
                message=e.message,
                detail=e.detail,
                retryable=False,
            ))
```

## 七、风险与对策

| 风险 | 等级 | 对策 |
|------|------|------|
| LLM 不支持原生 function calling | 中 | 保留旧 `parse_tool_calls` 作为 fallback；主流模型（GPT-4 / Claude / GLM / 通义千问）均支持 |
| 多轮推理导致 LLM 调用成本上升 | 中 | 设置 `MAX_TOOL_ROUNDS=8` 上限；只读工具不进入多轮循环 |
| 工具调用频率失控（LLM 死循环调用） | 高 | 每用户每小时调用上限 100 次；达到上限返回 blocked |
| 数据库迁移破坏现有数据 | 高 | 严格按 `database-migration-on-release.md` 流程；先备份；幂等脚本；`immutableAfterRelease: true` |
| 自动执行写操作导致误删 | 高 | 风险分级策略：写操作默认 confirm，仅只读 auto；删除类操作软删除可恢复 |
| 现有 prompt 与新协议不兼容 | 低 | 保留旧 `parse_tool_calls`；新 prompt 增加工具示例引导 |
| 前端 SSE 事件格式变更导致兼容性 | 中 | 同时发送新旧事件；前端做兼容处理；灰度上线 |
| `ai_cs_tool_call` 字段重命名丢数据 | 高 | V1.66 迁移前完整备份表；重命名前后双写一段时间；验证后再清理旧字段 |

### 9.5 名词解释

- **function calling**：OpenAI Chat Completions API 的原生工具调用协议，LLM 在响应中返回 `tool_calls` 字段，应用执行后通过 `role=tool` 消息回灌
- **Agent Loop**：LLM 与工具的循环交互，支持多步骤任务（查询 → 决策 → 执行 → 反馈 → 再决策）
- **ReAct**：Reasoning + Acting 模式，LLM 先思考再调用工具
- **traceId**：全链路追踪 ID，贯穿单次对话的所有工具调用
- **AccountContext**：统一账号上下文，封装 user_id 兜底、cookie_status 校验、自动选号
- **风险分级**：auto / confirm / blocked 三级，决定工具执行是否需要用户确认
