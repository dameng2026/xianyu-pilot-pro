## 一、前置假设

1. 本文按用户目标保留完整范围，不把目标缩减为单页优化或单接口补洞。
2. 本文建议采用**分阶段闭环交付**，而不是一次性横向重构全项目。
3. `消息等待` 暂按参考项目中的 `message_expire_time` 解释为：
   - 同一会话中，相同消息在设定时间窗口内不重复触发自动回复
   - 配置入口位于账号维度
   - 主要用于自动回复去重与冷却，而不是发货前确认等待
4. 如果用户后续明确要求 `消息等待` 指向“发货前等待确认”或“延迟发送”，则仅调整第二阶段设计，不影响第一阶段订单与发货闭环设计。

## 二、现状判断

### 2.1 当前项目已有但不完整的能力

当前项目并不是从零开始，已经具备以下基础：

- `user-web` 已有账号、消息、订单、自动发货、发货记录、发货模板、发货声明、定时任务页面。
- `core-api` 已有订单、自动发货规则、商品级发货配置、发货记录、发货声明、定时任务等控制器。
- `automation-service` 已有旧风格订单接口、消息接口、商品擦亮接口、自动发货基础接口。

但这些能力大多存在以下问题：

- 页面存在，接口口径分裂，前后端未统一收口。
- 实体和返回字段偏薄，无法支撑参考项目中的完整场景。
- 同一业务在 `core-api` 和 `automation-service` 中同时存在旧入口和新入口。
- 浏览器侧虽然能打开页面，但距离“真实数据 + 真实执行闭环”仍有差距。

### 2.2 参考项目提供的关键增强能力

参考项目中，目标相关能力主要分布在以下模块：

## 四、推荐改造路径

### 4.1 不推荐的路径

#### 路径 A：先做底座大重构

优点：

- 长远结构更统一
- 重复逻辑更少

缺点：

- 早期无法形成可见成果
- 真实浏览器验收会被推迟
- 风险高，容易陷入长期迁移

#### 路径 B：先补所有页面入口

优点：

- 短期看起来进度快

缺点：

- 容易出现“能点但不好用”的假完工
- 后端口径会继续分裂

### 4.2 推荐路径：分阶段闭环

#### 第一阶段：订单与发货闭环

覆盖：

- 订单管理
- 定时任务
- 定时补发货
- 发货配置（文本/卡密）
- 自动发货
- 闲鱼同步发货状态
- 商品多规格
- 多数量发货
- 手动发货 / 查看详情

#### 第二阶段：账号与聊天闭环

覆盖：

- 账号密码登录
- 人脸验证
- 在线聊天头像
- 聊天记录图片
- 发送图片
- 消息等待

#### 第三阶段：运营与风控能力

覆盖：

- 自动评价
- 商品擦亮
- 消息过滤
- 通知渠道

### 4.3 推荐理由

推荐分阶段闭环，原因如下：

1. 每个阶段都能形成真实可测链路。
2. 第一阶段覆盖范围最大、业务价值最高、和现有代码最接近。
3. 第一阶段完成后，后续账号与聊天、通知与过滤能力可以复用更稳定的订单和发货基线。

## 五、第一阶段详细设计：订单与发货闭环

### 5.1 范围

第一阶段只收口订单与发货相关链路，不触碰全部子系统。

包含：

- 订单列表增强
- 订单详情增强

- 自动发货
- 定时补发货
- 平台发货状态同步
- 多规格展示
- 多数量发货
- 定时任务扩容

### 5.2 架构职责

#### `core-api`

继续作为对外业务编排层，负责：

- 页面查询
- 订单与发货聚合视图
- 定时任务管理
- 发货记录与状态汇总
- 调用 `automation-service` 执行真实外部动作

#### `automation-service`

继续作为闲鱼侧执行器，负责：

- 同步闲鱼订单
- 执行文本发货 / 卡密发货
- 回传平台状态
- 处理真实执行异常与外部接口差异

### 5.3 第一阶段后端模块收口

#### `OrderReadService`

职责：

- 统一订单列表和详情读取
- 聚合规格、数量、发货状态、失败原因、同步时间

落点：

- 基于 `XianyuTradeOrderService`
- 不再让页面直接拼装多个接口结果

#### `OrderSyncService`

职责：

- 拉取闲鱼卖出订单
- 刷新单个订单详情
- 同步平台真实状态

#### `DeliveryCommandService`

职责：

- 手动发货
- 自动发货
- 定时补发货
- 发货重试
- 统一创建和推进 `delivery_record`

#### `DeliveryReconcileService`

职责：

- 比较本地发货记录与平台真实状态
- 更新订单展示状态
- 输出异常提示

### 5.4 数据模型方向

当前实体偏薄，第一阶段以数据库真实字段为准，补齐返回模型和查询口径。

### 5.5 核心数据流

#### 手动发货

订单详情页发起手动发货：

1. `core-api` 校验订单、商品配置、库存与幂等锁
2. 创建 `manual` 类型发货记录
3. 调用 `automation-service` 执行真实发货
4. 回写发货记录
5. 刷新订单详情聚合状态
6. 触发平台状态校验

#### 自动发货

扫描已付款订单：

1. 命中商品发货配置
2. 创建 `after_payment` 待处理记录
3. 执行器处理
4. 成功或失败都落记录
5. 不允许只改订单主表而不留记录

#### 定时补发货

任务扫描失败或部分成功记录：

1. 筛选符合补发策略的记录
2. 创建重试执行
3. 重试结果继续落记录
4. 前端可追踪重试次数和补发结果

#### 平台状态同步

手动或定时触发：

1. 拉取平台订单状态
2. 与本地记录做对账
3. 更新订单状态和异常提示

#### 多规格 / 多数量

- 规格：先完成“展示闭环”
- 数量：按订单数量驱动发送次数
- 文本型允许重复模板发送
- 卡密型按库存逐个占用，允许部分成功

### 5.8 异常处理

1. 发货需要幂等锁，避免同一订单重复发货。
2. 多数量发货必须支持“部分成功”。
3. 卡密库存不足要区分“完全失败”和“执行中耗尽”。
4. 平台同步失败不能覆盖本地真实发货结果。
5. 定时任务失败必须保留运行日志和错误原因。
6. 兼容期内旧 `/order/*` 与新 `/orders/*` 只能共享同一服务层。

## 九、当前结论

基于当前代码证据，最合理的推进顺序是：

1. 先做订单与发货闭环
2. 再做账号与聊天闭环
3. 最后做运营与风控能力

这样可以在每个阶段结束时都形成真实可测的功能闭环，而不是只完成静态页面或半成品接口。
