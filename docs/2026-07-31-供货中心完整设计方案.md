## 一、背景与目标

### 1.1 业务背景

平台需要构建"供货中心"，允许用户自主上传货源（文本/卡密）并进行 C2C 交易，打通从上传、审核、上架到交易结算的完整闭环。

### 1.2 核心需求

1. **供货中心页面**：个人信息板 + 统计卡片（已上传数/今日收入/收入趋势/账户余额），余额与个人中心实时同步
2. **货源上传与管理**：支持文本货源/卡密货源，自定义价格；支持改价、补库存、下架
3. **审核机制**：上传后进后台审批队列，通过后上架到货源商城，驳回附原因通知
4. **交易结算**：买家购买后支付金额进入供货商余额，7 天冷冻期后解冻可提现
5. **资金展示**：可用余额 + 冻结余额清晰展示
6. **退款机制**：买家可申请退款，卖家响应；冷冻期内资金从冻结额扣回

### 1.3 设计原则（基于平台定位的简化策略）

本平台为小平台，采用轻量化策略：
- **不设平台介入仲裁**：退款纠纷由买卖双方协商，无法解决引导联系客服微信
- **不设业务风控**：不检测刷单、恶意退款、价格异常（用户量小，人工关注即可）
- **不允许欠款**：余额不足则退款失败，平台不垫付
- **退款窗口 = 冷冻期 7 天**：超出 7 天禁止退款，平台不予监管
- **所有提现人工审核打款**：无需套现风控

## 二、整体架构

### 2.1 七大子模块

| 模块 | 核心职责 | 与现有体系的关系 |
|------|---------|----------------|
| **M1 货源管理** | 供货商上传/编辑/下架/补库存/改价；销量与库存看板 | 复用 `card_group`/`card_item` 卡密认领机制；新建 `supply_product` 表 |
| **M2 审核中心** | 后台审批队列；驳回附原因+通知；审核状态追踪 | 新建 `audit_record` 表 + admin-web 审核工作台 |
| **M3 交易订单** | C2C 下单、支付、发货、确认收货、自动完结 | 新建 `trade_order` 表（与闲鱼 `xianyu_trade_order` 隔离） |
| **M4 资金托管** | 买家付款冻结 → 卖家发货 → 确认收货入冷冻期 → 7 天后解冻 → 平台抽佣分账 | 新建 `trade_balance` + `cash_balance_ledger` + `TradeEscrowService` |
| **M5 提现** | 交易货款提现申请、人工审核、打款、失败回滚 | 新建 `trade_withdrawal_request`（与推广分成提现隔离） |
| **M6 退款协商** | 买家申请退款；卖家同意/拒绝；资金从冻结额扣回 | 新建 `trade_refund`；无平台介入 |
| **M7 消息通知** | 关键节点触达供货商与买家 | 复用 `notification` + `notify_dispatcher` + SSE；新增 9 个事件类型 |

### 2.3 关键隔离原则

- 供货中心资金**独立于**推广分成资金，避免提现额度互相挤占
- 供货中心商品**与平台自营商品合并展示**在货源商城，但底层表隔离（`supply_product` vs `mall_product`）
- 供货中心交易**独立于**闲鱼订单镜像，本平台内闭环结算

## 三、核心设计决策

### 决策 1：商品表设计 —— 新建 `supply_product`

供货商品与平台自营商品（`mall_product`）底层表隔离，但在货源商城前台合并展示。

**理由**：现有 `mall_product` 设计之初是 `tenant_id=0` 的平台自营商品，无 `seller_id`。强行扩展会让所有现有查询都要加 `WHERE seller_id IS NULL` 过滤自营，技术债累积。新建独立表 + 前台 UNION 查询合并展示，既隔离又统一。

**前台合并展示**：
- `supply_product` 和 `mall_product` 都加 `weight` 字段（展示权重）
- 货源商城列表接口 UNION 两表，按 `weight DESC, sort_order DESC, created_time DESC` 排序
- 统一返回结构中加 `source` 字段（`mall` / `supply`）标识来源
- 后台可分别调整两类商品的 weight

### 决策 2：资金账户设计 —— 新建 `trade_balance`

与推广分成资金（`growth_user_balance`）物理隔离。

**理由**：参照现有 `growth_user_balance` 的设计模式（已有成功先例），新建 `trade_balance` 保持一致风格。前端"个人中心"展示余额时调用聚合接口合并展示。

### 决策 3：提现表设计 —— 新建 `trade_withdrawal_request`

与推广分成提现（`growth_withdrawal_request`）隔离。

**理由**：推广分成提现的"打款失败回滚"逻辑与交易货款不同（交易货款涉及冷冻期资金已解冻才可提），状态机不能混。

### 决策 4：7 天冷冻期 + 退款联动机制

**核心规则**：
- 订单确认收货 → 资金进入 `frozen_balance`，`unfreeze_at = NOW() + 7天`
- 7 天内无退款申请 → 定时任务扫描解冻到 `available_balance`
- **7 天内买家发起退款 → 冷冻期自动延长**，资金保持冻结，直到退款处理结束
- 退款同意 → 从 `frozen_balance` 扣回退给买家；部分退款则剩余部分解冻给卖家
- 退款拒绝/撤销 → 退款结束，重新计算解冻时间（已过 7 天则立即解冻）
- **超出 7 天未发起退款 → 禁止退款**，资金解冻后平台不予监管

**关键简化**：退款资金处理始终从 `frozen_balance` 扣，不存在"已解冻需从 available 扣"的复杂场景。

### 决策 5：无平台介入，双方协商

退款流程无平台仲裁环节：
- 买家申请退款 → 卖家同意/拒绝 → 结束
- 卖家拒绝或双方无法达成一致 → 前端固定展示"如有异议，添加客服微信：JiShu0724"
- 后台仅查看退款记录，不提供仲裁功能

### 决策 6：平台抽佣机制

每笔订单结算时按 `commission_rate`（默认 5%，可后台配置）抽佣。

- 订单金额 `amount_cent` → 平台抽佣 `platform_fee_cent = amount_cent * commission_rate` → 卖家到账 `seller_income_cent = amount_cent - platform_fee_cent`
- 抽佣在"确认收货入冷冻期"时计算并记录，**不立即入平台账户**，随资金解冻同步入账
- 平台抽佣也走 `cash_balance_ledger` 流水（`change_type='platform_commission'`），便于对账

### 决策 7：不允许欠款

- 退款时若 `frozen_balance` 不足（理论上不会发生，因为退款延长冷冻期，资金始终冻结）→ 退款失败
- 余额不足时不垫付、不欠款，提示联系客服

## 四、数据模型设计

### 4.1 新建表清单（8 张）

#### 表 1：`supply_product`（供货商品表）

```sql
CREATE TABLE IF NOT EXISTS supply_product (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    seller_id BIGINT NOT NULL COMMENT '供货商用户ID',
    product_type VARCHAR(10) NOT NULL DEFAULT 'text' COMMENT 'text=文本货源, card=卡密货源',
    title VARCHAR(200) NOT NULL,
    subtitle VARCHAR(200) DEFAULT '',
    content TEXT COMMENT '商品描述/正文',
    delivery_content TEXT COMMENT '文本货源的发货内容',
    cover_url VARCHAR(500) DEFAULT '',
    images_json JSON COMMENT '商品图片数组',
    category VARCHAR(50) DEFAULT '' COMMENT 'AI分类',
    price_cent BIGINT NOT NULL DEFAULT 0 COMMENT '售价(分)',
    stock INT NOT NULL DEFAULT -1 COMMENT '库存(-1=无限,文本货源默认-1)',
    card_group_id BIGINT NULL COMMENT '卡密货源关联的 card_group.id',
    audit_status VARCHAR(20) NOT NULL DEFAULT 'pending' COMMENT 'pending/rejected/approved',
    audit_reason VARCHAR(500) DEFAULT '' COMMENT '驳回原因',
    audit_at DATETIME NULL,
    auditor_id BIGINT NULL,
    status TINYINT NOT NULL DEFAULT 0 COMMENT '0=下架,1=上架(仅 audit_status=approved 时可上架)',
    weight INT NOT NULL DEFAULT 0 COMMENT '展示权重(越大越靠前,后台可调)',
    bought_count INT NOT NULL DEFAULT 0 COMMENT '销量',
    rating_avg DECIMAL(3,2) DEFAULT 5.00 COMMENT '平均评分',
    rating_count INT DEFAULT 0,
    sort_order INT DEFAULT 0,
    commission_rate DECIMAL(5,4) DEFAULT 0.0500 COMMENT '单品抽佣率(默认5%),0=用全局配置',
    created_time DATETIME,
    updated_time DATETIME,
    deleted TINYINT NOT NULL DEFAULT 0,
    INDEX idx_supply_seller(seller_id, deleted, audit_status),
    INDEX idx_supply_status(audit_status, status, deleted),
    INDEX idx_supply_category(category, status, deleted),
    INDEX idx_supply_card_group(card_group_id),
    INDEX idx_supply_weight(weight, status, deleted)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='供货商品表';
```

**关键设计**：
- `audit_status` 与 `status` 双字段：审核通过后才能上架，避免"上架即审核通过"的耦合
- `card_group_id` 复用现有卡密仓库体系，供货商可关联自有卡密组
- `commission_rate` 支持单品费率，0 时回退全局配置
- `weight` 字段用于货源商城合并展示时的排序，后台可调

#### 表 2：`trade_order`（C2C 交易订单表）

```sql
CREATE TABLE IF NOT EXISTS trade_order (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    order_no VARCHAR(64) NOT NULL UNIQUE COMMENT '订单号 supply_yyyyMMdd_xxx',
    buyer_id BIGINT NOT NULL,
    seller_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    product_source VARCHAR(10) NOT NULL DEFAULT 'supply' COMMENT 'supply=供货商品, mall=平台自营',
    product_snapshot JSON COMMENT '下单时商品快照(title/price/type)',
    quantity INT NOT NULL DEFAULT 1,
    amount_cent BIGINT NOT NULL COMMENT '订单总额(分)',
    platform_fee_cent BIGINT NOT NULL DEFAULT 0 COMMENT '平台抽佣(分)',
    seller_income_cent BIGINT NOT NULL DEFAULT 0 COMMENT '卖家到账(分)',
    escrow_status VARCHAR(20) NOT NULL DEFAULT 'unpaid' COMMENT 'unpaid/frozen/released/refunded',
    pay_method VARCHAR(20) DEFAULT '' COMMENT 'balance/wechat/alipay',
    paid_time DATETIME NULL,
    delivered_time DATETIME NULL COMMENT '卖家发货时间',
    confirmed_time DATETIME NULL COMMENT '买家确认收货时间',
    auto_completed TINYINT DEFAULT 0 COMMENT '是否自动完结',
    freeze_end_time DATETIME NULL COMMENT '冷冻期结束时间(=confirmed_time+7天,有退款时延长)',
    released_time DATETIME NULL COMMENT '资金解冻时间',
    refund_status VARCHAR(20) DEFAULT 'none' COMMENT 'none/requested/agreed/rejected/closed',
    buyer_remark VARCHAR(500) DEFAULT '',
    created_time DATETIME,
    updated_time DATETIME,
    INDEX idx_trade_buyer(buyer_id, escrow_status),
    INDEX idx_trade_seller(seller_id, escrow_status),
    INDEX idx_trade_product(product_id, product_source),
    INDEX idx_trade_status(escrow_status, refund_status),
    INDEX idx_trade_freeze(freeze_end_time, escrow_status, refund_status) COMMENT '定时任务扫描冷冻期'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='C2C交易订单';
```

**关键设计**：
- `escrow_status` 状态机：`unpaid`(待支付) → `frozen`(已支付冻结中) → `released`(已解冻给卖家) / `refunded`(已退款)
- `product_source` 标识商品来源（供货商品 vs 平台自营），方便资金流向区分
- `product_snapshot` 保存下单时商品快照，避免后续商品改价/下架影响订单
- `freeze_end_time` 用于定时任务扫描解冻，**有退款时设为 NULL 表示延期**
- `refund_status` 与 `escrow_status` 联动：退款进行中时冷冻期延长

#### 表 3：`trade_balance`（用户交易余额聚合表）

```sql
CREATE TABLE IF NOT EXISTS trade_balance (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    available_balance BIGINT NOT NULL DEFAULT 0 COMMENT '可提现余额(分)',
    frozen_balance BIGINT NOT NULL DEFAULT 0 COMMENT '冷冻中余额(7天解冻,退款延长)',
    withdrawing_balance BIGINT NOT NULL DEFAULT 0 COMMENT '提现中余额',
    withdrawn_amount BIGINT NOT NULL DEFAULT 0 COMMENT '累计已提现',
    total_income BIGINT NOT NULL DEFAULT 0 COMMENT '累计交易收入(含抽佣前)',
    version INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    created_time DATETIME,
    updated_time DATETIME,
    UNIQUE KEY uk_trade_balance_user(user_id),
    INDEX idx_trade_balance_tenant(tenant_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户交易余额聚合';
```

**关键设计**：
- 4 个余额字段，覆盖所有资金状态
- `version` 乐观锁，配合 `FOR UPDATE` 行锁防并发
- 与 `growth_user_balance` 设计模式一致
- **无 `debt_amount` 字段**（不允许欠款）

#### 表 4：`cash_balance_ledger`（现金账户流水表）

```sql
CREATE TABLE IF NOT EXISTS cash_balance_ledger (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    change_type VARCHAR(40) NOT NULL COMMENT 'trade_freeze/trade_release/trade_refund_out/trade_refund_in/withdraw/withdraw_refund/platform_commission/manual_adjust',
    change_amount BIGINT NOT NULL COMMENT '变动金额(分,正=入账,负=出账)',
    before_balance BIGINT NOT NULL,
    after_balance BIGINT NOT NULL,
    balance_field VARCHAR(20) NOT NULL COMMENT 'available/frozen/withdrawing',
    ref_type VARCHAR(40) DEFAULT '' COMMENT 'trade_order/withdrawal/refund/manual',
    ref_id BIGINT NULL,
    ref_no VARCHAR(64) DEFAULT '' COMMENT '关联单号',
    remark VARCHAR(500) DEFAULT '',
    created_time DATETIME,
    INDEX idx_cash_user(user_id, created_time),
    INDEX idx_cash_type(change_type, created_time),
    INDEX idx_cash_ref(ref_type, ref_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='现金账户流水';
```

**关键设计**：
- `balance_field` 标注本次变动影响哪个余额字段（available/frozen/withdrawing）
- 与现有 `token_balance_ledger` 设计模式一致，便于对账
- 平台抽佣也记录在此表中（`user_id=0` 表示平台账户）

#### 表 5：`trade_frozen_record`（资金冻结记录表）

```sql
CREATE TABLE IF NOT EXISTS trade_frozen_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL COMMENT '卖家ID',
    order_id BIGINT NOT NULL,
    order_no VARCHAR(64) NOT NULL,

    frozen_at DATETIME NOT NULL COMMENT '冻结时间(=确认收货时间)',

    status VARCHAR(20) NOT NULL DEFAULT 'frozen' COMMENT 'frozen/released/refunded',

    unfreeze_job_id VARCHAR(64) DEFAULT '' COMMENT '定时任务ID(幂等)',
```

**关键设计**：

- 状态机简化：`requested` → `agreed`(同意) / `rejected`(拒绝) / `closed`(买家撤销)
- **无 `disputed` 状态**（无平台介入）
- **无仲裁人字段**

#### 表 8：`audit_record`（通用审核记录表）

## 五、关键业务流程

### 5.1 货源上传-审核-上架流程

```
供货商上传货源
  → 写 supply_product (audit_status='pending', status=0)
  → 写 audit_record (module_key='supply_product', status='pending')
  → 通知后台审核员（站内信 + SSE）
  → 后台审核工作台处理：
      ├─ 通过 → supply_product.audit_status='approved', audit_record.status='approved'
      │        → 通知供货商"审核通过,可上架"
      │        → 供货商手动点击上架 → status=1 → 商品进入货源商城（与平台自营合并展示）
      └─ 驳回 → supply_product.audit_status='rejected', audit_reason='xxx'
               → audit_record.status='rejected', reason='xxx'
               → 通知供货商"审核未通过: xxx, 请修改后重新提交"
               → 供货商编辑后重新提交 → audit_status 回到 'pending', 新增一条 audit_record
```

**审核 SLA**：建议后台 24 小时内处理，超时在仪表盘高亮提醒。

**已上架商品改价/补库存**：
- 改价：直接更新 `price_cent`，**无需重新审核**（但记录操作日志）
- 补卡密库存：通过 `card_group` 关联，新增 `card_item` 即可，无需审核
- 修改商品标题/描述/封面：**需重新审核**（避免上架后改成违规内容）

### 5.2 购买-资金冻结-发货-冷冻-解冻-提现主流程

```
① 买家下单
  → 校验商品 status=1 && audit_status='approved' && (stock>0 || stock=-1)
  → 卡密货源：校验 card_group 库存 >= quantity
  → 写 trade_order (escrow_status='unpaid')
  → 调用现有 PaymentService.createOrder(order_type='supply_product')

② 买家支付
  → 支付成功回调 → trade_order.escrow_status='frozen', paid_time=NOW()
  → 卡密货源：原子认领 card_item (status 0→1→2)（复用现有 claimUnusedCard 逻辑）
              → 写 delivery_record, trade_order.delivered_time=NOW()
  → 文本货源：直接发送 delivery_content, delivered_time=NOW()
  → 写 cash_balance_ledger (卖家, change_type='trade_freeze', balance_field='frozen', +seller_income_cent)
  → trade_balance.frozen_balance += seller_income_cent（卖家）
  → 通知买卖双方

③ 确认收货 / 自动完结
  → 买家点击确认 或 72 小时后自动完结
  → trade_order.confirmed_time=NOW(), escrow_status 仍为 'frozen'
  → freeze_end_time = NOW() + 7天
  → 创建 trade_frozen_record (frozen_at=NOW(), unfreeze_at=NOW()+7天, status='frozen')
  → 通知卖家"资金已进入7天冷冻期"

④ 7 天冷冻期到期（定时任务每 10 分钟扫描）
  → 扫描 trade_frozen_record WHERE status='frozen' AND unfreeze_at IS NOT NULL AND unfreeze_at<=NOW()
  → 且订单无进行中退款（refund_status NOT IN ('requested')）
  → trade_order.escrow_status='released', released_time=NOW()
  → trade_frozen_record.status='released', released_at=NOW()
  → trade_balance.frozen_balance -= amount, available_balance += amount
  → 写 cash_balance_ledger (change_type='trade_release', balance_field='available', +amount)
  → 同步入账平台抽佣: cash_balance_ledger (平台账户 user_id=0, change_type='platform_commission', +platform_fee_cent)
  → 通知卖家"资金已解冻,可提现"

⑤ 卖家提现
  → 校验 available_balance >= amount && amount >= min_withdrawal_amount
  → trade_balance.available_balance -= amount, withdrawing_balance += amount
  → 写 trade_withdrawal_request (status='pending')
  → 后台人工审核 → 通过 → 人工打款 → status='paid', withdrawing_balance -= amount, withdrawn_amount += amount
                 → 驳回 → status='rejected', available_balance += amount, withdrawing_balance -= amount
```

### 5.3 退款流程（冷冻期内，退款延长冷冻期）

```
买家申请退款 (trade_refund.status='requested')
  → 校验：订单确认收货时间 + 7天 > NOW()（冷冻期内才能申请）
  → trade_order.refund_status='requested'
  → trade_frozen_record.unfreeze_at = NULL（延期解冻）, extended_by_refund=1
  → 通知卖家响应

卖家响应：
  ├─ 同意全额退款
  │   → trade_refund.status='agreed', trade_order.refund_status='agreed', escrow_status='refunded'
  │   → trade_frozen_record.status='refunded', remaining_amount_cent=0
  │   → trade_balance.frozen_balance -= amount
  │   → 退款给买家（原路退回 或 退到买家 trade_balance.available_balance）
  │   → 写 cash_balance_ledger (卖家, 'trade_refund_out', 'frozen', -amount)
  │   → 写 cash_balance_ledger (买家, 'trade_refund_in', 'available', +amount) [余额退回场景]
  │   → 平台抽佣不入账（取消）
  │
  ├─ 同意部分退款（amount_cent < 订单金额）
  │   → trade_refund.status='agreed', trade_order.refund_status='agreed'
  │   → trade_frozen_record.remaining_amount_cent -= refund_amount
  │   → 从 frozen_balance 扣 refund_amount 退给买家
  │   → 剩余冻结金额解冻给卖家：frozen_balance -= remaining, available_balance += remaining
  │   → trade_frozen_record.status='released', unfreeze_at=NOW()
  │   → 平台抽佣按比例入账
  │
  ├─ 拒绝退款
  │   → trade_refund.status='rejected', trade_order.refund_status='rejected'
  │   → trade_frozen_record.unfreeze_at 恢复计算（已过7天则立即解冻, 否则保持原值）
  │   → extended_by_refund=0
  │   → 通知买家"卖家拒绝退款,如有异议请联系客服微信: JiShu0724"
  │
  └─ 买家撤销退款
      → trade_refund.status='closed', trade_order.refund_status='closed'
      → trade_frozen_record.unfreeze_at 恢复计算（同上）
      → extended_by_refund=0
```

**超出 7 天禁止退款**：
- 前端：订单详情页在确认收货 7 天后隐藏"申请退款"按钮
- 后端：退款申请接口校验 `confirmed_time + 7天 > NOW()`，否则返回错误"已超出退款期限"

**资金始终从 `frozen_balance` 扣**：
- 因为退款延长冷冻期，资金不会在退款处理期间解冻
- 不存在"已解冻需从 available 扣"的场景
- 不允许欠款，不需要平台垫付

| `EVENT_TRADE_REFUND_RESOLVED` | 退款已处理 | 买家 | 卖家同意/拒绝退款 |
| `EVENT_TRADE_WITHDRAWAL_RESULT` | 提现审核结果 | 供货商 | 提现通过/驳回/打款 |

### 9.2 通知渠道策略

- **站内信**：所有事件必发（写入 `notification` 表 + SSE 实时推送）
- **外部渠道**（webhook/飞书/钉钉/邮件）：仅在用户 `user_notification_setting` 中开启对应事件时发送
- **去重**：高频事件（如"新订单"）按 `(user_id, event_type, ref_id)` 去重，避免重复打扰

## 十、技术保障（非业务风控）

### 10.1 资金对账

- 所有资金变动必写 `cash_balance_ledger` 流水
- 每日定时对账任务校验 `SUM(ledger) == trade_balance` 各字段
- 对账不平告警通知管理员

### 10.2 并发保障

| 风险点 | 保障措施 |
|--------|---------|
| 卡密并发下单 | `card_item` 原子 `UPDATE status=1 WHERE status=0` 认领（复用现有机制） |
| 余额并发 | `trade_balance` 行锁 `FOR UPDATE` + 乐观锁 `version` |
| 重复支付 | `trade_order.order_no` 唯一 + 支付回调幂等 |
| 重复退款 | `trade_refund.refund_no` 唯一 + 退款操作幂等 |
| 定时任务重复执行 | Redis 分布式锁 + `unfreeze_job_id` 幂等字段 |

### 10.3 数据一致性

- 资金操作事务化：余额变动 + 流水写入在同一事务
- 卡密认领 + 订单状态更新在同一事务
- 退款资金处理 + 冻结记录更新在同一事务

## 十三、关键风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 资金对账不平 | 所有资金变动必写 `cash_balance_ledger`；每日定时对账任务校验 `SUM(ledger) == trade_balance` |
| 定时任务重复执行 | Redis 分布式锁 + `unfreeze_job_id` 幂等字段 |
| 卡密库存与订单不一致 | 下单时原子认领 + 发货失败回滚 `card_item.status` 0←1 |
| 退款延长冷冻期逻辑遗漏 | 定时任务扫描时 `WHERE unfreeze_at IS NOT NULL` 排除延期的记录 |
| 货源商城 UNION 查询性能 | 两表均加 `weight` + `status` + `deleted` 索引；分页查询限制 |
| 余额并发超扣 | `trade_balance` 行锁 + 乐观锁 + 流水先写后更新余额 |

## 十四、设计决策汇总

| 决策项 | 最终方案 |
|--------|---------|
| 商品表 | 新建 `supply_product`，与 `mall_product` 底层隔离，前台 UNION 合并展示 |
| 商品权重 | 两表都加 `weight` 字段，后台可调，控制货源商城展示顺序 |
| 资金账户 | 新建 `trade_balance`，与推广分成 `growth_user_balance` 隔离 |
| 提现表 | 新建 `trade_withdrawal_request`，与推广分成提现隔离 |
| 冷冻期 | 7 天，定时任务扫描解冻；退款延长冷冻期（`unfreeze_at=NULL`） |
| 退款窗口 | = 冷冻期 7 天，超出禁止退款 |
| 退款资金 | 始终从 `frozen_balance` 扣（退款延长冷冻期保证资金冻结） |
| 平台介入 | 无，双方协商，引导联系客服微信 JiShu0724 |
| 业务风控 | 无（小平台策略） |
| 欠款机制 | 不允许欠款，余额不足退款失败 |
| 平台抽佣 | 默认 5%，可后台配置，随资金解冻同步入账 |
| 提现审核 | 所有提现人工审核打款 |
