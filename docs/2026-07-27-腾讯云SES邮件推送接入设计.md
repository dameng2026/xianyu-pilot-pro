# 腾讯云 SES 邮件推送接入设计

- 日期：2026-07-27
- 状态：设计完成，待用户审阅
- 目标：在现有邮件配置功能中增加腾讯云 SES，并同时支持管理员验证码邮件与用户级业务通知邮件
- 设计范围：core-api、admin-web、automation-service、user-web
- 不包含：生产部署、腾讯云控制台模板创建、密钥轮换、Git 提交

## 1. 背景与现状

项目目前存在两条独立的邮件链路，不能合并为一条配置：

| 链路 | 用途 | 发送实现 | 配置位置 | 配置入口 |
|---|---|---|---|---|
| 管理员级邮件 | 登录、注册、找回密码验证码 | Java `jakarta.mail` | `sys_config.email_config` | admin-web `/system/email-config` |
| 用户级业务通知 | Cookie 到期、新订单、自动发货、Token 预警等 | Python `smtplib` | `user_notification_setting.config_json` | user-web 通知设置 |

现有管理员邮件配置服务为 `NotificationConfigService`，邮件发送服务为 `EmailSenderService`。管理员测试邮件由 `EmailSenderService.sendTestEmail()` 实际发送；用户级业务通知由 automation-service 的 `notify_dispatcher.py` 分发，并写入 `notification_delivery_log`。

腾讯云 SES 使用 Java SDK 通过 HTTPS API 发送，与 SMTP 的连接参数、认证方式和模板参数均不同，因此采用“发送方式切换”模型，不把 SES 伪装成 SMTP 服务商。

## 2. 已确认的产品决策

1. 管理员级验证码邮件和用户级业务通知邮件都接入腾讯云 SES。
2. 现有 SMTP 保留，管理员可在 SMTP 与腾讯云 SES 之间切换。
3. 管理员级验证码邮件使用腾讯云模板发送。
4. 用户级业务通知使用 SES HTML 直发，不要求每种业务事件创建腾讯云模板。
5. 腾讯云 SES 为全局唯一配置，由管理员在 admin-web 中维护。
6. 用户级通知复用管理员的腾讯云 SES 凭据，用户不填写 SecretId 和 SecretKey。
7. Java core-api 是唯一可以解密腾讯云 SecretKey 并调用 SES 的服务。
8. 不新增业务数据库表；扩展现有 JSON 配置结构，兼容已有 SMTP 配置。
9. 不在前端、Python 配置、日志或异常响应中暴露 SecretKey。

## 3. 总体架构

```text
管理员配置页面
  → POST /admin-api/system/email-config
  → NotificationConfigService
  → sys_config.email_config

验证码发送
  → UserAuthService
  → EmailSenderService
      ├─ provider=smtp → jakarta.mail
      └─ provider=tencent_ses → TencentSesSender → 腾讯云 SES SendEmail

用户级业务通知
  → automation-service notify_dispatcher.py
      ├─ sendMode=smtp → 现有 smtplib 流程
      └─ sendMode=tencent_ses → Java 内部邮件代理接口
                              → 读取并解密全局 SES 配置
                              → TencentSesSender
                              → 腾讯云 SES SendEmail
```

### 3.1 Java 组件边界

新增 `TencentSesSender`，只负责腾讯云 SDK 客户端初始化、请求构造、调用和错误归一化；不负责读取数据库。

`EmailSenderService` 保留现有统一入口，根据 `provider` 路由到 SMTP 或 SES，避免调用方感知具体发送方式。

`NotificationConfigService` 负责配置 JSON 的读写、敏感字段加密、脱敏和 SES 配置完整性判断。

新增内部邮件代理服务或接口层，负责为 automation-service 提供“使用全局 SES 发送业务通知”的受控能力。该接口只接受收件人、主题和正文，不接受任何云凭据。

### 3.2 Python 组件边界

`notify_dispatcher.py` 继续负责事件匹配、模板渲染、去重、投递日志和结果处理。

当邮件渠道的 `sendMode` 为 `tencent_ses` 时，Python 只调用 Java 内部代理接口；不得读取 `sys_config.email_config`，不得持有 SecretKey，不得直接调用腾讯云 SDK。

### 3.3 前端组件边界

admin-web 邮件配置页面维护 SMTP 和 SES 的配置表单，并根据 `provider` 显示对应字段。

user-web 通知设置页面仅显示腾讯云 SES 是否可用，并允许用户选择 SMTP 或腾讯云 SES；SES 模式只要求收件人，不展示全局凭据。

## 4. 管理员配置数据模型

配置仍保存在 `sys_config`：

```text
config_key = email_config
config_value = JSON
```

完整配置结构如下：

```json
{
  "provider": "tencent_ses",
  "smtpHost": "smtp.qq.com",
  "smtpPort": 465,
  "encryption": "ssl",
  "fromEmail": "",
  "fromName": "闲鱼助手",
  "username": "",
  "password": "",
  "tencentSecretId": "",
  "tencentSecretKey": "",
  "tencentRegion": "ap-hongkong",
  "tencentFromEmailAddress": "noreply@example.com",
  "tencentTemplateId": 12345,
  "subject": "【闲鱼助手】验证码通知",
  "template": "",
  "codeLength": 6,
  "validSeconds": 300,
  "sendInterval": 60,
  "dailyLimit": 20
}
```

字段规则：

| 字段 | 规则 |
|---|---|
| `provider` | `smtp` 或 `tencent_ses`；缺失时按 `smtp` 兼容 |
| `tencentSecretId` | 全局腾讯云 SecretId，按敏感字段脱敏返回 |
| `tencentSecretKey` | 使用 `CookieCryptoService` 加密存储，GET 不返回明文 |
| `tencentRegion` | 默认 `ap-hongkong`，保存时校验非空 |
| `tencentFromEmailAddress` | 腾讯云 SES 已验证发件地址 |
| `tencentTemplateId` | 验证码模板 ID，必须为正整数 |
| `fromName` | SMTP 发件人名称；SES 可作为显示名称的可选配置 |
| SMTP 字段 | 全部保留，切换发送方式不清理原配置 |
| 验证码业务字段 | `subject`、`template`、`codeLength` 等继续保留 |

### 4.1 敏感字段存储

`NotificationConfigService.saveEmailConfig()` 扩展现有敏感字段处理逻辑，同时处理：

- `password` / `clearPassword`
- `tencentSecretKey` / `clearTencentSecretKey`

保存规则：

1. 新提交明文时加密后保存。
2. 表单留空且未勾选清除时保留数据库已有密文。
3. 勾选清除时保存空值。
4. 接口返回 `passwordConfigured`、`tencentSecretKeyConfigured`，不返回明文。
5. SecretId 返回脱敏值或空值，不返回完整凭据。

### 4.2 配置完整性

SMTP 模式完整条件：

```text
smtpHost、fromEmail、username、password 均非空
```

腾讯云 SES 模式完整条件：

```text
tencentSecretId、tencentSecretKey、tencentRegion、
tencentFromEmailAddress、tencentTemplateId 均有效
```

`EmailSenderService.isEmailConfigured()` 根据当前 `provider` 判断。这样 `UserAuthCapabilityService` 可以继续根据该方法决定邮箱验证码能力是否开放。

## 5. 用户级业务通知数据模型

用户级配置仍位于 `user_notification_setting.config_json` 的 email channel 中：

```json
{
  "type": "email",
  "enabled": true,
  "sendMode": "tencent_ses",
  "smtpHost": "",
  "smtpPort": 465,
  "smtpUser": "",
  "smtpPass": "",
  "fromEmail": "",
  "receiver": "user@example.com"
}
```

规则：

- `sendMode` 为 `smtp` 或 `tencent_ses`。
- `sendMode` 缺失时按 `smtp` 兼容旧配置。
- SMTP 模式沿用现有用户级 SMTP 字段和加密逻辑。
- SES 模式不保存 SecretId、SecretKey、Region 或 TemplateID。
- `receiver` 是业务通知的收件人。
- SES 模式下 `fromEmail` 为空时使用管理员全局 SES 发件地址；如果填写，则必须经过后端策略校验，默认实现建议优先使用全局发件地址，避免未经验证的发件地址被拒绝。

## 6. 腾讯云 SDK 与发送流程

### 6.1 Maven 依赖

在 `apps/core-api/pom.xml` 增加：

```xml
<dependency>
    <groupId>com.tencentcloudapi</groupId>
    <artifactId>tencentcloud-sdk-java-ses</artifactId>
    <version>3.1.1371</version>
</dependency>
```

版本固定为用户提供的版本，后续升级需单独验证 SDK API 兼容性。

### 6.2 TencentSesSender

建议接口职责：

```text
sendVerificationEmail(config, toEmail, code)
sendHtmlEmail(config, toEmail, subject, htmlContent, textContent)
```

验证码邮件请求：

```text
FromEmailAddress = tencentFromEmailAddress
Destination      = [toEmail]
TemplateID       = tencentTemplateId
TemplateData     = {"code":"123456"}
```

用户级业务通知请求：

```text
FromEmailAddress = tencentFromEmailAddress
Destination      = [toEmail]
Subject          = 业务事件主题
Simple.Message   = HTML正文和纯文本正文
```

具体请求字段以 SDK 3.1.1371 的 `SendEmailRequest` 模型为准；实现前需要通过 Maven 依赖解析或 SDK 源码确认 HTML 直发字段名称，不能仅凭文档示例猜字段。

### 6.3 验证码发送

`EmailSenderService.sendVerificationCode()` 流程：

1. 读取解密后的管理员配置。
2. 根据 `provider` 判断 SMTP 或 SES。
3. SMTP 继续执行现有模板替换和重试逻辑。
4. SES 生成模板变量 `{"code":"验证码"}`，调用 `TencentSesSender.sendVerificationEmail()`。
5. 捕获腾讯云 SDK 异常，转换为统一的友好错误。
6. 日志仅记录脱敏收件人、provider、错误分类和请求结果，不记录密钥、完整请求体或签名。

### 6.4 测试邮件

后台测试发送接口仍为：

```text
POST /admin-api/system/email-config/test
```

测试逻辑根据当前 `provider` 发送：

- SMTP：发送现有测试 HTML 内容。
- SES：使用已配置的验证码模板发送测试验证码，或在 SDK 支持的情况下使用 HTML 直发测试内容；测试链路必须与当前 provider 实际链路一致。

测试接口在保存配置之前不能验证尚未保存的表单值，页面应继续提示先保存配置再发送测试邮件。

## 7. Java 内部 SES 邮件代理

### 7.1 接口建议

建议新增内部路由：

```text
POST /internal/notification/email/tencent-ses
```

请求：

```json
{
  "toEmail": "user@example.com",
  "subject": "新订单通知",
  "htmlContent": "<html>...</html>",
  "textContent": "新订单通知"
}
```

响应：

```json
{
  "success": true,
  "messageId": "腾讯云返回的MessageId"
}
```

失败响应只返回稳定的业务错误码和友好原因，不返回腾讯云请求签名、SecretId、SecretKey、完整堆栈或可能包含敏感信息的原始响应。

### 7.2 安全控制

内部接口必须同时满足：

1. 不加入普通用户公开 API 白名单。
2. 使用现有服务间认证机制；如果当前项目已有 automation-service 到 core-api 的内部鉴权，应复用该机制。
3. 若当前没有专用服务间认证，则增加固定内部请求认证配置，并通过环境变量提供，不得硬编码密钥。
4. 只接受邮件地址、主题、HTML 和纯文本正文。
5. 后端强制使用 `sys_config.email_config` 的全局 SES 配置。
6. provider 不是 `tencent_ses` 时拒绝发送。
7. 对收件人格式、主题长度、HTML 正文长度做校验。
8. 发送失败不得泄露云 SDK 原始异常到用户端。

### 7.3 Python 调用

`notify_dispatcher.py` 的 SES 分支调用 Java 代理接口：

```text
sendMode=smtp
  → 现有 SMTP 发送

sendMode=tencent_ses
  → core-api 内部邮件代理
  → 统一处理成功、失败、重试和投递日志
```

Python 端不应实现腾讯云签名，不应安装腾讯云 Java SDK 对应的替代库，也不应从数据库读取管理员邮件配置。

## 10. 出站网络与配置

### 10.1 Java 出站策略

现有 `OutboundNotificationPolicy` 主要校验 SMTP/Webhook。腾讯云 SES SDK 使用 HTTPS API，需要加入 SES API 域名校验。

建议：

- 允许的 API 主机固定为腾讯云 SES 官方域名。
- 仅允许 HTTPS 443。
- 不允许通过前端或用户配置自定义 SES API Host。
- 对 SDK 实际解析出的 endpoint 做固定域名校验。

如果 SDK 内部不经过项目自定义出站策略，则至少在发送器初始化前对 Region 做白名单校验，只允许受支持的腾讯云地域格式，并固定使用官方 SDK endpoint。

### 10.2 Python 出站策略

Python 不直接访问腾讯云 SES，只访问 core-api 内部代理，因此不需要在 Python 端增加腾讯云密钥或 SDK 配置。内部代理地址沿用项目现有服务间通信配置。

## 11. 错误处理与重试

### 11.1 错误分类

统一分为：

| 类型 | 处理 |
|---|---|
| 配置不完整 | 不重试，提示管理员完成配置 |
| SecretId/SecretKey 无效 | 不重试，提示检查腾讯云密钥 |
| 发件地址未验证 | 不重试，提示验证发件地址 |
| TemplateID 无效或未审核 | 不重试，提示检查模板 |
| 收件地址无效 | 不重试，返回邮箱格式错误 |
| 频率/配额限制 | 按有限次数退避重试，最终记录失败 |
| HTTPS 超时或临时网络错误 | 最多 2 次重试，指数退避 |
| 腾讯云服务端 5xx | 最多 2 次重试，指数退避 |
| 内部代理不可达 | Python 记录投递失败，不泄露内部异常 |

### 11.2 验证码链路

验证码发送失败时，前台只收到友好提示；后台日志保留 provider、收件人脱敏值、错误类别和腾讯云 RequestId（如果 RequestId 不含敏感信息）。

### 11.3 业务通知链路

业务通知发送失败时：

1. 不阻塞订单、自动发货等主业务流程。
2. 写入 `notification_delivery_log`。
3. 记录 `channel_key=email`、发送方式、事件类型、失败状态和重试次数。
4. 遵循现有通知去重策略。
5. 不在日志中记录 SecretKey 或完整 HTML 中可能包含的敏感用户数据，具体日志内容遵循现有脱敏策略。

user-web：

- 平台 SES 可用时可选择腾讯云 SES。
- 平台 SES 不可用时给出明确提示。
- 用户不能看到平台凭据。
- 旧 SMTP 配置显示和保存不受影响。

## 13. 数据库与迁移策略

本功能首版不新增数据库迁移脚本：

- 管理员配置继续使用 `sys_config.email_config` JSON。
- 用户级配置继续使用 `user_notification_setting.config_json` JSON。
- `notification_delivery_log` 已有字段足够记录渠道和结果。

因此：

- 不修改已发布迁移脚本。
- 不新增 `migrations-manifest.json` 条目。
- 不需要执行数据库结构迁移。
- 仍需在实现验证阶段确认已有 JSON 读写兼容旧数据。

如果未来需要持久化 SES 模板、发送统计或服务商级配额，再单独设计追加迁移，不能把这些需求隐式塞入本次改造。

## 14. 安全要求

1. 用户提供的腾讯云 SecretId/SecretKey 不写入 Git、前端构建产物、截图或普通日志。
2. 不使用用户消息中的示例 SecretId 作为项目默认配置。
3. SecretKey 只能来自管理员配置保存后的加密值。
4. 不允许 HTTP 接口接收并转发云密钥。
5. 不在错误响应中返回腾讯云 SDK 原始完整异常。
6. 发送日志只记录收件人脱敏值和错误分类。
7. SES API endpoint 不允许由用户自定义。
8. 用户级配置只能引用全局 SES 能力，不能提升为凭据管理入口。
9. 继续遵守现有 SMTP/出站网络白名单策略。
10. 部署前如需生产上线，必须另行执行项目规定的维护模式、数据库备份迁移和数据同步 Token 检查流程；本设计阶段不执行上线。

## 16. 验收标准

功能完成后必须满足：

1. 管理员可以在 admin-web 选择 SMTP 或腾讯云 SES。
2. SMTP 原有配置和发送行为保持正常。
3. 腾讯云 SES 配置可保存、脱敏读取、清除和校验。
4. 管理员级验证码可以通过腾讯云模板发送。
5. 管理员测试邮件可以根据当前发送方式真实发送。
6. 用户级邮件通知可以选择 SMTP 或腾讯云 SES。
7. 用户级 SES 通知复用管理员全局凭据，不暴露凭据。
8. 用户级业务通知使用 HTML 直发，主题和正文正确。
9. 发送失败有明确分类、有限重试和投递日志。
10. 旧配置无需重新填写即可继续工作。
11. Java、Python、admin-web、user-web 的 lint/typecheck/build/test 通过项目现有命令。
12. 代码中不存在硬编码腾讯云 SecretId、SecretKey 或测试密钥。
13. 不新增破坏性数据库操作，不清空任何现有业务数据。

## 17. 待实现阶段确认项

以下事项在写实现计划或编码前需要根据项目实际代码确认，不改变总体设计：

1. core-api 当前是否已有 automation-service 专用内部鉴权，内部代理接口应复用其实现。
2. 腾讯云 SDK 3.1.1371 中 HTML 直发对应的确切字段名称，需要以实际依赖模型为准。
3. Java 网关是否要求所有响应拆包为 `data` 字段，内部代理接口需要遵守现有网关约定。
4. Python 到 core-api 的服务地址和超时配置应复用现有内部 HTTP 客户端。
5. 用户级邮件通知当前 SMTP 密码的加密/解密路径需要确认，SES 分支不能破坏该路径。
6. 腾讯云 SES 模板是否支持当前验证码变量命名，最终按腾讯云控制台模板变量要求配置为 `code`。

## 18. 结论

本设计通过在现有邮件配置 JSON 上增加 provider 和 SES 字段，以 Java 为唯一凭据持有和 SES 调用方，同时保留旧 SMTP 链路，实现管理员验证码和用户业务通知两条链路的腾讯云 SES 接入。

核心收益：

- 不新增数据库表，升级风险低。
- 不破坏现有 SMTP 用户。
- 管理员只维护一套全局腾讯云凭据。
- 用户级通知不接触敏感密钥。
- 验证码使用腾讯云模板，满足事务性邮件场景。
- 业务通知使用 HTML 直发，避免创建大量腾讯云模板。
- 发送失败、日志、重试和安全边界均可复用现有体系。
