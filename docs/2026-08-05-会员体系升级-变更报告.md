## 二、数据库变更（V1.69）

迁移文件：`apps/core-api/src/main/resources/db/migration/V1.69__membership_vip_single_store_limit.sql`

1. 新增套餐：
   - `vip-single`：VIP（单店版），月/季/年 = 999/2599/8888 分，`max_xianyu_accounts=1`，功能开关与 VIP 相同。
2. 调整套餐：
   - `normal`：免费，`max_xianyu_accounts=1`，介绍含“闲鱼店铺数量：1 个”。
   - `vip`：1999/3999/13888 分，`max_xianyu_accounts=0`（不限），介绍含“闲鱼店铺数量：不限制”。
   - `svp/svip`：3999/9999/29999 分，`max_xianyu_accounts=0`（不限）。
3. 功能管理配置：在 `admin_module_record`（`user_feature_switch`）JSON 中注入首行 `store-limit`（`normal=1, vipSingle=1, vip=0, svp=0`，`0=无限制`）。
4. 已登记 `db/migrations-manifest.json`（V1.69，含 SHA-256）；`scripts/validate_migrations.py` 校验通过。

本地开发库已实际执行该迁移：

## 三、Java 后端（core-api）

### 1. FeatureSwitchService
- 功能清单新增首行 `store-limit`（店铺数量配置行），并在管理端/用户端返回 `vipSingle` 字段（与 `vip` 一致）。
- `normalizeConfig` 持久化 `vipSingle` 与 `storeLimitNormal/VipSingle/Vip/Svp` 数字字段；`initDefaultsIfAbsent` 同步初始化。
- `store-limit` 行不参与页面访问控制。
- 新增方法：
  - `resolveUserPlanCode(userId)`：返回原始套餐编码（含 `vip-single`）。
  - `getStoreLimits()` / `storeLimitForPlanCode(code)`：读取店铺数配置（0=不限）。
  - `getStoreLimitStatus(userId)`：返回 `{planCode, level, levelName, limit, unlimited, accountCount}`。
  - `assertCanAddAccount(userId)`：超限抛 `BizException(400, ...)`，`data.errorCode=STORE_LIMIT_REACHED`。
- 权限归一：`vip-single` 在功能权限判定中等同 `vip`；`level` 返回归一化值。

### 2. XianyuAccountService
- `create()`、`createFromCookie()`（新增或恢复软删除店铺）执行店铺数量校验。
- 重新扫码/更新已有账号不校验。

### 3. FeatureSwitchController
- 新增用户端接口 `GET /api/feature-switches/store-limit`。

### 4. UserProfileService / SysUserService / AdminModuleService
- `vip_level=3` 映射为 `vip-single`（VIP（单店版）），`1` 仍为 VIP、`2` 为 SVP/SVIP。
- 用户等级展示支持“VIP（单店版）”。

### 5. BillingPlanService
- 套餐排序支持 `vip-single`（普通 < 单店版 < VIP < SVIP）。
- `level` 返回 `vip-single`；返回 `maxXianyuAccounts` / `storeLimit` 字段。

### 6. AiScenePricingService
- `vip-single` 归一化为 `vip`，保证 AI 场景定价与 VIP 一致。

### 7. SchemaCompatibilityRunner
- 新增 `vip-single` 种子套餐；对齐 `normal/vip/svp` 的 `max_xianyu_accounts`；更新 AI 客服“会员权益说明”为四档文案。

### 8. StoreLimitCleanupScheduler（新增）
- `@Scheduled` 每 10 分钟检查，默认执行时间 `2026-08-07T00:00:00`（即 8 月 6 日 24 点），可用配置 `xianyu.store-limit.cleanup-after` 调整。
- 对每个用户按等级店铺上限计算超限数量，保留策略：Cookie 可用 > 最近活跃（最后登录/心跳/更新时间）> id 倒序。
- 多余店铺通过 `XianyuAccountService.delete` 软删除（同时停自动化、软删 auth/runtime，可恢复）。
- 状态记录在 `admin_module_record`（`store_limit_cleanup`）：`running/done/failed`，幂等、并发安全。

## 四、Python 自动化服务（automation-service）

新增 `app/services/store_limit.py`：
- 与 Java 一致的店铺数配置读取（`admin_module_record` 的 `store-limit` 行）与默认值。
- 用户等级解析：`sys_user.vip_level`（3=单店版、2=SVIP、1=VIP）优先，其次有效订阅套餐。
- `assert_can_add_store(db, user_id)` 返回 `STORE_LIMIT_REACHED` 结构化错误。

接入点：
- `misc.py::_save_scan_login_result`：扫码确认后“新建账号”或“恢复软删除账号”前校验。
- `restful.py::restful_create_account`：REST 创建账号前校验。

## 九、风险与说明

- 店铺“移除”采用现有软删除语义（`deleted=1`），账号数据、商品/订单关联保留在库中，可恢复；被移除店铺的自动化连接会停止。
- 清理保留策略为“最活跃店铺优先”，如业务上更希望保留“最早创建”或“指定店铺”，需在 `StoreLimitCleanupScheduler` 中调整排序。
- 后台功能管理中「VIP（单店版）」列当前为 VIP 联动只读，若后续需要单店版独立开关，可在后端去掉 `vipSingle` 派生逻辑并放开该列编辑。
- 已存在的 `ai_cs_knowledge` 中 V1.45/V1.46 的少量历史文案（如“普通最多 3 个账号”）未逐一改写；会员权益核心入口已更新，历史知识条目如影响客服回答可在后续统一刷新。
